# CLARSLIB

Блочный архиватор на Rust: словарное кодирование **LZ77**, энтропийное кодирование **rANS**, защита **Reed–Solomon с 10 информационными и 2 проверочными фрагментами**. Формат архива — **CLARSv02**, расширение — `.mrx`.

Документ описывает реализацию из `src/`. Все размеры ниже даны в байтах, если явно не указаны биты. Численные примеры используют ASCII, а не UTF-8-представление русских букв.

## 1. Сборка и команды

Требуется **Rust 1.88 или новее**. Версии зависимостей закреплены в `Cargo.toml` и `Cargo.lock`.

```sh
cargo build --release --locked
cargo test --test all --locked
```

Исполняемый файл: `target/release/arch` (`arch.exe` в Windows).

```sh
# Создать архив из файла и папки; LZ77 и rANS включены, RS выключен.
arch create backup.mrx report.txt photos

# Те же этапы с защитой; 4 рабочих потока.
arch create --protect --threads 4 backup.mrx report.txt photos

# Только rANS, без LZ77.
arch create --no-lz77 backup.mrx report.txt

# Без сжатия, но с защитой RS.
arch create --no-lz77 --no-rans --protect backup.mrx report.txt

# Просмотреть записи и полностью проверить читаемость потока.
arch info --threads 4 backup.mrx

# Извлечь в новую папку.
arch extract --threads 4 backup.mrx restored

# Имя источника, начинающееся с --, после разделителя не является параметром.
arch create -- backup.mrx --notes.txt
```

`--no-lz77`, `--no-rans` и `--protect` относятся к `create`; они должны стоять перед именем архива. `--threads T` допускается один раз до разделителя `--`, `1 ≤ T ≤ 64`. Без параметра используется `min(available_parallelism, 64)`, при невозможности определить параллельность — 1.

Если у имени архива нет расширения, добавляется `.mrx`; другое расширение отклоняется. Создание не перезаписывает существующий файл. Для извлечения нужна **несуществующая** папка. При ошибке созданный архив или папка извлечения удаляется; если удаление не удалось, это сообщается вместе с исходной ошибкой.

`info` не ограничивается чтением оглавления: оно декодирует блочный поток и проходит содержимое файлов, но не записывает файлы на диск. Статистика «Исправлено фрагментов» считает RS-фрагменты, а не исправленные байты.

## 2. Задача, модель и обозначения

### 2.1. Что является источником

Источник — не строка символов языка, а последовательность **байтов записей файлов и папок**. Имя кодируется UTF-8; содержимое файла не преобразуется. Поток записей разрезается на блоки до 64 КиБ. Запись, имя или содержимое могут пересекать границу блока.

![Модель данных и этапы кодирования](docs/figures/data.svg)

| Обозначение | Смысл |
|---|---|
| `X`, `N = |X|` | Исходный блок потока записей; `1 ≤ N ≤ 65536` |
| `C`, `K = |C|` | Кандидат после включённых этапов сжатия |
| `Y`, `S = |Y|` | Сохранённые данные **до** RS; `1 ≤ S ≤ N` |
| `n` | Длина входа отдельного вызова rANS; не обязательно равна `N` |
| `D` | Число разных байтов во входе rANS |
| `v(s)`, `f(s)`, `c(s)` | Число появлений, нормализованная частота, начало интервала |
| `M = 4096` | Сумма нормализованных частот rANS |
| `L = 2²³` | Нижняя граница и начальное состояние rANS |
| `q` в rANS | Остаток `x mod M` |
| `q` в RS | Длина одного фрагмента; контекст раздела отличает её от остатка |
| `T` | Число рабочих потоков |

### 2.2. Информация и кодирование

Для модели источника без памяти с вероятностями $p_s$ информация появления символа и энтропия равны:

$$
I(s)=-\log_2 p_s,\qquad H=-\sum_s p_s\log_2 p_s.
$$

При равномерном алфавите из $D$ символов $H=\log_2 D$. Это характеристика модели, **не обещание фактического размера архива**. Для независимых символов идеальная стоимость сообщения $s_0\ldots s_{n-1}$ составляет

$$
\ell_{\mathrm{ideal}}=-\sum_{i=0}^{n-1}\log_2 p_{s_i}.
$$

В архиваторе rANS использует $p_s=f(s)/4096$. В реальном потоке дополнительно нужны длина, алфавит, частоты и состояние, а на уровне архива — записи имён, заголовки и, при включении, защита. На коротком сообщении служебные данные могут превосходить выигрыш.

LZ77 уменьшает повторяемость цепочек и меняет распределение байтов. rANS кодирует уже полученный поток, а не исходные буквы файла. Reed–Solomon, напротив, **добавляет избыточность** для восстановления; это не алгоритм сжатия. Разделение «источник → кодер сжатия → кодер защиты» соответствует учебной постановке ОТИК [1, с. 5–7, 15–16; 2, с. 3, 11].

## 3. Конвейер и выбор представления

Для блока $X$ сначала применяются только включённые этапы:

$$
C=\operatorname{rANS}_{\mathrm{opt}}(\operatorname{LZ77}_{\mathrm{opt}}(X)),
\qquad
Y=\begin{cases}C,& |C|<N,\\X,& |C|\ge N.\end{cases}
$$

Отключённый этап — тождественное преобразование. Кодер не перебирает комбинации «только LZ77», «только rANS», «оба» внутри одного блока: комбинация задаётся флагами архива. Сравниваются только итоговый кандидат этой комбинации и исходный блок.

![Выбор представления блока](docs/figures/v2-pipeline.svg)

**Правило декодера:** `S < N` означает сжатое представление; тогда выполняются rANS, затем LZ77, если их флаги включены. При `S = N` оба этапа пропускаются. Отдельного бита «этот блок сжат» нет.

RS применяется к выбранному $Y$ независимо от результата сравнения. Словарь LZ77 и модель rANS не переносятся в следующий блок. Это позволяет обрабатывать блоки независимо и ограничивает размер исходного блока, но исключает ссылки LZ77 через его границу.

Сравнение `K < N` происходит до RS. Размер защищённого блока монотонно зависит от `S`, поэтому меньший `S` не увеличивает его размер, но из-за заполнения фрагментов уменьшение `S` не всегда уменьшает физический размер защищённого блока.

## 4. LZ77: словарь, поиск и восстановление

Реализация: [`src/lz77/mod.rs`](src/lz77/mod.rs), [`src/lz77/matcher.rs`](src/lz77/matcher.rs). Вариант — последовательность троек **`(l, d, c)`**: длина совпадения, расстояние назад, следующий явный байт. Порядок не следует путать с записью `(d, l, c)` в некоторых учебных источниках.

### 4.1. Ограничения ссылки

В позиции $p$ выбирается самое длинное совпадение в окне:

$$
\begin{aligned}
0&\le l\le\min(255,N-p-1),\\
1&\le d\le\min(4096,p)\quad(l>0),\\
X[p-d+j]&=X[p+j]\quad(0\le j<l),\\
c&=X[p+l],\qquad p'=p+l+1.
\end{aligned}
$$

Верхняя граница `N − p − 1` оставляет один байт для `c`. Поэтому каждая тройка заканчивается литералом, в том числе последняя. При `l = 0` расстояние не записывается; математически можно обозначать его нулём, но в потоке этого поля нет.

![Окно и параметры ссылки LZ77](docs/figures/lz77-overview.svg)

Это соответствует идее «ссылка на повторное вхождение + следующий символ», но конкретные границы и способы записи полей определены реализацией [3, с. 1–4, 7–8]. Здесь **нет флагового байта** с группой признаков литералов и ссылок.

### 4.2. Поиск совпадения

Хешируются первые два байта:

$$
h(a,b)=\left(\big((a+256b)\times\mathtt{0x9E3779B1}\big)\bmod 2^{32}\right)\gg20.
$$

Получаются 4096 цепочек позиций. Хеш лишь отбирает кандидатов: реальное совпадение проверяется побайтово, поэтому коллизия не превращается в неправильную ссылку.

1. Если допустимая длина не меньше 2, пройти цепочку от новых позиций к старым, пока расстояние не превышает 4096.
2. Сравнить байты до `limit`; заменить лучший результат только при **строго большей** длине.
3. При достижении `limit` поиск закончить — более длинного ответа нет.
4. Если совпадение длины ≥ 2 не найдено, проверить последнюю позицию текущего байта. Она может дать ссылку длины 1.
5. Внести в таблицы **все** пройденные позиции `p … p + l`, а не только начало тройки.

При равных длинах сохраняется ближайшая ссылка. Лимита числа кандидатов нет; окно ограничено, но неблагоприятное распределение хешей может увеличить стоимость поиска. Выбор «самая длинная ссылка» не является глобальной оптимизацией размера всего потока.

![Блок-схема кодирования LZ77](docs/figures/lz77-alg.svg)

### 4.3. Поток и стоимость тройки

```text
N : unsigned LEB128
повторять до конца потока:
    l : u8
    если l > 0: d : unsigned LEB128
    c : u8
```

Если $v(d)$ — число байтов varint, то тройка занимает

$$
t(l,d)=\begin{cases}2,&l=0,\\2+v(d),&l>0.\end{cases}
$$

Она описывает $l+1$ исходных байтов. Без учёта префикса и влияния последующего rANS локальный выигрыш есть при $l+1>2+v(d)$. Например, ссылка длины 1 может увеличить поток LZ77. Кодер её всё равно записывает; окончательный выбор представления делает блочный уровень.

Наихудшая верхняя граница выхода LZ77 для блока — `3 + 2 × 65536 = 131075` байт: трёхбайтовая длина и по два байта на каждый литерал. Поэтому длина входа rANS после LZ77 может быть больше 65536.

### 4.4. Декодирование и перекрытие

После чтения тройки проверяются допустимое расстояние и `l + 1 ≤ N − |R|`. Копирование выполняется **по одному байту**:

$$
\text{повторить }l\text{ раз: }R\leftarrow R\,\|\,R[|R|-d],
\qquad R\leftarrow R\,\|\,c.
$$

Текущий `|R|` увеличивается после каждого добавления. Поэтому при `l > d` источник следующих байтов может находиться среди только что восстановленных данных. Копирование фиксированного среза старого буфера не эквивалентно этому правилу.

![Блок-схема декодирования LZ77](docs/figures/lz77-flow.svg)

### 4.5. Разбор ABABABA

| `p` | `limit` | `l` | `d` | `c` | Новая позиция |
|---:|---:|---:|---:|:---:|---:|
| 0 | 6 | 0 | — | A | 1 |
| 1 | 5 | 0 | — | B | 2 |
| 2 | 4 | 4 | 2 | A | 7 |

```text
07 | 00 41 | 00 42 | 04 02 41
 N    l  c    l  c    l  d  c
```

При третьей тройке буфер равен `AB`. Копируются позиции 0, 1, 2, 3, причём позиции 2 и 3 появились в ходе этой же ссылки. Затем литерал `A` завершает результат.

![Пошаговое перекрывающееся копирование](docs/figures/lz77.svg)

Весь LZ77-поток занимает **8 байт для 7 байт входа**. Это корректный учебный пример обратимости, но не пример сжатия. Без rANS блочный кодер сохранит исходные 7 байт.

Другие проверяемые случаи:

- `AAAAAA → 06 00 41 04 01 41`: длина ссылки 4, расстояние 1.
- 258 байт `A`: первая тройка-литерал, ссылка длины 255 с литералом, последний литерал.
- На позиции 6 в `abXabYabZ` выбирается `d = 3`, а не 6 при одинаковой длине 2.
- При `limit = 0` совпадение не ищется: последний байт записывается явно.

## 5. rANS: модель, состояние и перенормировка

Реализация: [`src/rans/mod.rs`](src/rans/mod.rs), [`src/rans/model.rs`](src/rans/model.rs). **rANS не является арифметическим интервальным кодером из лекции ОТИК.** Они используют вероятностную модель и интервалы частот, но rANS кодирует символы взаимно обратными переходами целочисленного состояния. Вложенное сужение вещественного интервала из арифметического кодирования здесь не выполняется [4, с. 2–9, 15].

### 5.1. Статическая модель блока

Для ненулевого входа длины $n$ подсчитываются $v(s)$ и число присутствующих байтов $D$. Отсутствующим символам назначается частота 0. Присутствующим сначала назначается:

$$
\begin{aligned}
w_s&=v(s)(M-D),\\
f_s^{(0)}&=1+\left\lfloor\frac{w_s}{n}\right\rfloor,\\
r_s&=w_s\bmod n,\\
\Delta&=M-\sum_s f_s^{(0)},\qquad M=4096.
\end{aligned}
$$

Добавить единицу первым $\Delta$ символам, отсортированным по убыванию $r_s$; при одинаковом остатке первым идёт меньший байт. Таким образом, каждая присутствующая частота положительна и сумма точно равна 4096. Положительность нужна для деления в переходе кодера; точная сумма — для полного разбиения таблицы состояний.

$$
c(s)=\sum_{t<s}f(t),\qquad [c(s),c(s)+f(s)).
$$

![Нормализация частот rANS](docs/figures/rans-alg.svg)

**Пример ASCII BANAN:** $n=5$, $D=3$, $M-D=4093$. Символы в порядке значения байта: A, B, N.

| Символ | `v` | `w` | `floor(w/n)` | Остаток | Начальная `f⁰` | Поправка | Итог `f` | `c` |
|:---:|---:|---:|---:|---:|---:|---:|---:|---:|
| A | 2 | 8186 | 1637 | 1 | 1638 | 0 | 1638 | 0 |
| B | 1 | 4093 | 818 | 3 | 819 | 1 | 820 | 1638 |
| N | 2 | 8186 | 1637 | 1 | 1638 | 0 | 1638 | 2458 |

Сумма начальных частот 4095; наибольший остаток у B. Получаются три непересекающихся интервала, вместе покрывающие `[0,4096)`.

![Модель BANAN и интервалы](docs/figures/rans-overview.svg)

### 5.2. Переходы без перенормировки

Кодер начинает с $x=L=2^{23}$ и обрабатывает вход **справа налево**. Для символа $s$:

$$
C_s(x)=\left\lfloor\frac{x}{f(s)}\right\rfloor M+(x\bmod f(s))+c(s).
$$

Декодер получает символы **слева направо**. Вычислить $q=x\bmod M$ и найти единственный $s$, для которого $c(s)\le q<c(s)+f(s)$. Затем:

$$
D_s(x)=f(s)\left\lfloor\frac{x}{M}\right\rfloor+q-c(s).
$$

**Почему переход обратим.** Пусть $x=af+r$, $0\le r<f$. Тогда $C_s(x)=aM+r+c$. Остаток по $M$ равен $r+c$, поскольку интервал символа лежит внутри `[0,M)`. Декодер выбирает тот же символ и получает $fa+(r+c)-c=af+r=x$.

### 5.3. Байтовая перенормировка

Чтобы состояние оставалось в 32-битном диапазоне, перед переходом кодер выполняет:

$$
\text{пока }x\ge 2^{19}f(s):\quad b=x\bmod256,\quad x\leftarrow\lfloor x/256\rfloor.
$$

Байт $b$ откладывается. Порог в реализации равен

$$
((L\gg12)\ll8)f(s)=2^{19}f(s).
$$

После обратного перехода декодер восстанавливает масштаб:

$$
\text{пока }x<L:\quad\text{прочитать }b,\quad x\leftarrow256x+b.
$$

Поток хранит конечное состояние `x : u32 LE`, затем отложенные байты **в обратном порядке их выдачи**. Декодер начинает с последнего состояния, поэтому ему сначала нужен последний вынесенный байт. Проверка начального состояния: $L\le x<256L=2^{31}$.

![Кодер, декодер и циклы перенормировки rANS](docs/figures/rans-flow.svg)

После вывода ровно $n$ символов требуется одновременно `x = L` и отсутствие непрочитанных байтов. Эти проверки выявляют многие повреждённые потоки, но не являются криптографической проверкой содержимого.

### 5.4. Пример ABAB: полный прямой и обратный проход

$f(A)=f(B)=2048$, $c(A)=0$, $c(B)=2048$. Перенормировка не нужна: все состояния перед кодированием меньше соответствующего порога.

| Шаг кодера | Символ | Состояние до | Состояние после |
|---:|:---:|---:|---:|
| 1 | B | 8388608 | 16779264 |
| 2 | A | 16779264 | 33558528 |
| 3 | B | 33558528 | 67119104 |
| 4 | A | 67119104 | 134238208 |

| Шаг декодера | Состояние до | `q` | Символ | Состояние после |
|---:|---:|---:|:---:|---:|
| 1 | 134238208 | 0 | A | 67119104 |
| 2 | 67119104 | 2048 | B | 33558528 |
| 3 | 33558528 | 0 | A | 16779264 |
| 4 | 16779264 | 2048 | B | 8388608 |

![Трасса состояния для ABAB](docs/figures/rans.svg)

```text
04 | 01 | 41 42 | 80 10 | 00 50 00 08
 n   D−1  алфавит  f(A)   x = 0x08005000, LE
```

Частота B не хранится: $4096-2048=2048$. Байт перенормировки отсутствует. Результат rANS — **10 байт**, поэтому на уровне блока для такого входа сохраняется исходное представление.

### 5.5. Пример с перенормировкой: AB, повторённое 16 раз

Вход — 32 байта, модель та же. На восьмом шаге кодера обрабатывается A:

```text
x = 1073915904 ≥ 2^19 × 2048 = 1073741824
выдать 00; x = floor(1073915904 / 256) = 4194984
C_A(x) = 8389288
```

Все вынесенные байты в порядке кодера: `00 A8 AA AA`. В потоке они стоят как `AA AA A8 00`. Конечное состояние — 8389290, то есть `AA 02 80 00` в LE.

```text
20 | 01 | 41 42 | 80 10 | AA 02 80 00 | AA AA A8 00
 n   D−1  алфавит  f(A)       состояние    байты масштаба
```

В первом шаге декодера выбирается A: `q = 682`. Обратный переход даёт 4194986 < L; чтение первого `AA` восстанавливает `256 × 4194986 + 170 = 1073916586`. Затем восстанавливается B, и процесс продолжается. После 32 символов состояние снова равно L, все четыре байта прочитаны. Выход rANS занимает **14 байт**, меньше 32; это пример реального выигрыша **при отключённом LZ77**. При включённом LZ77 вход rANS будет другим.

### 5.6. Двоичное представление модели

```text
n : varint
если n = 0: поток заканчивается здесь (единственный байт 00)
D − 1 : u8
если D ≤ 32: D разных байтов по возрастанию
иначе: bitmap[32]; символ s задан битом (s mod 8) в байте floor(s / 8)
f(s₀), …, f(s_{D−2}) : varint
x : u32 LE
байты перенормировки
```

Последняя частота вычисляется вычитанием из 4096. При `D = 1` частоты в потоке вообще не нужны: единственный символ имеет частоту 4096. Проверяются порядок алфавита, число битов карты, `D ≤ n`, положительность частот и наличие четырёх байтов состояния.

Длина отдельного потока rANS ограничена длиной возможного выхода LZ77; минимальный ненулевой заголовок — 7 байт (`n`, `D−1`, один символ, состояние). Предельная консервативная оценка заголовка в коде — 550 байт. Это верхняя оценка, а не фиксированная длина модели.

## 6. CRC32: обнаружение повреждений

Реализация использует `crc32fast 1.4.2`. Контрольная сумма вычисляется **отдельно для каждого RS-фрагмента**, включая два проверочных. Она хранится как `u32 LE` в таблице перед фрагментами.

CRC32 соответствует отражённому алгоритму IEEE: начальный регистр `0xFFFFFFFF`, отражённый полином `0xEDB88320`, финальный XOR `0xFFFFFFFF`. При табличном вычислении очередного байта $b$:

$$
i=(crc\mathbin{\&}255)\oplus b,
\qquad crc'=(crc\gg8)\oplus TABLE[i].
$$

Таблица эквивалентна восьми битовым шагам с полиномом для каждого возможного младшего байта. Это математическое описание результата; библиотека может использовать оптимизированное исполнение.

![Вычисление CRC32](docs/figures/crc32-flow.svg)

Контрольный вектор: ASCII `123456789` даёт **`0xCBF43926`**, в LE — `26 39 F4 CB`. Для пустого входа результат равен 0.

CRC **обнаруживает**, но не исправляет. Несовпадение сообщает RS, какой фрагмент считать отсутствующим. Коллизии возможны; CRC не защищает от умышленной подмены. Без `--protect` таблицы CRC нет, и неверные, но синтаксически допустимые данные могут быть приняты.

## 7. GF(256) и Reed–Solomon

Реализация: [`src/ecc.rs`](src/ecc.rs), зависимость `reed-solomon-erasure 6.0.0`, модуль `galois_8`. Используется **систематический erasure-код RS(12,10)**: 10 исходных фрагментов и 2 проверочных. Известные позиции повреждений получаются по CRC.

Учебный материал ОТИК объясняет конечные поля, систематическое кодирование и различие информационных и проверочных символов [2, с. 22–30; 5, с. 2–14; 6, с. 1–8]. Полиномиальный декодер синдромов из курса не является алгоритмом этой библиотеки: здесь восстановление основано на обращении матрицы известных строк.

### 7.1. Арифметика поля

Каждый байт — многочлен степени < 8 с коэффициентами в GF(2):

$$
a=a_7z^7+\cdots+a_1z+a_0,\qquad a_i\in\{0,1\}.
$$

Модуль поля библиотеки:

$$
P(z)=z^8+z^4+z^3+z^2+1\quad(\mathtt{0x11D}).
$$

Сложение и вычитание совпадают с XOR. Умножение — произведение многочленов с остатком по $P(z)$. Для ненулевого $a$, $a^{255}=1$ и $a^{-1}=a^{254}$. Например,

$$
\mathtt{0x80}\times\mathtt{0x02}=z^8\equiv z^4+z^3+z^2+1=\mathtt{0x1D}.
$$

Это **29**, а не результат обычного умножения целых 128 × 2 с обрезанием до байта.

![Байт и операции GF(256)](docs/figures/reed-solomon.svg)

### 7.2. Как готовятся фрагменты

1. Добавить перед выбранным payload $Y$ его длину $S$ как `u32 LE`.
2. Выбрать $q=\lceil(S+4)/10\rceil$; для блоков `S ≥ 1`, поэтому `q ≥ 1`.
3. Дополнить нулями до `10q` байт и разрезать на $D_0,\ldots,D_9$ по $q$ байт.
4. Получить $P_0,P_1$, тоже по $q$ байт.
5. Записать 12 CRC32 в порядке $D_0,\ldots,D_9,P_0,P_1$, затем сами фрагменты в том же порядке.

![Подготовка и кодирование RS payload](docs/figures/rs-erasure-encode.svg)

Нулевое заполнение здесь **есть**: оно нужно для одинаковой длины фрагментов. Префикс $S$ позволяет убрать его после восстановления. Это не последовательность укороченных кодовых слов по 223 байта.

### 7.3. Порождающая матрица

Для каждого смещения $j$ берётся столбец из 10 байтов $\mathbf d_j$. Библиотека строит матрицу Вандермонда и приводит её к систематическому виду:

$$
V_{i,k}=i^k\text{ в GF(256)},\quad
0\le i<12,\ 0\le k<10,\qquad
T=V_{0:10,:},\quad G=VT^{-1}=\begin{bmatrix}I_{10}\\G_p\end{bmatrix}.
$$

Число $i$ в этой формуле — элемент поля с байтовым представлением `i`; $i^0=1$, включая строку `i=0`. Верхние 10 строк единичные, поэтому исходные фрагменты остаются без изменения. Нижние две строки в десятичном представлении байтов:

```text
P0: 129 150 175 184 210 196 254 232   3   2
P1: 150 129 184 175 196 210 232 254   2   3
```

$$
P_r[j]=\bigoplus_{k=0}^{9}G_p[r,k]\cdot D_k[j],\qquad r\in\{0,1\}.
$$

![Систематическая матрица RS(12,10)](docs/figures/reed-solomon-flow.svg)

Коэффициенты привязаны к версии библиотеки и её полю. Нельзя заменить эти строки «обычной суммой байтов» или формулой другой реализации RS и получить совместимый поток.

### 7.4. Восстановление и его предел

При чтении CRC каждого фрагмента сравнивается с таблицей. Несовпавший фрагмент заменяется на `None`. Если таких фрагментов больше двух, возвращается ошибка. При одном или двух библиотека выбирает исправные строки матрицы и восстанавливает неизвестные данные. При нуле реконструкция не вызывается.

Пусть $J$ — любые 10 исправных строк, $\mathbf y_J$ — соответствующие байты. Тогда

$$
\mathbf d=G_J^{-1}\mathbf y_J.
$$

После реконструкции информационные фрагменты объединяются, читается внутренний $S$; проверяется $S\le10q-4$ и возвращается соответствующий срез. Внутренний размер не сравнивается непосредственно с аргументом `_original_size`; дальнейшие проверки блочного и энтропийного декодирования ограничивают допустимость результата.

![Проверка CRC и декодирование стираний](docs/figures/rs-erasure-decode.svg)

Для абстрактного кода с двумя проверочными символами условие исправления смешанных ошибок и стираний имеет вид $2t+e\le2$, где $t$ — ошибки с неизвестными позициями, $e$ — известные стирания. **Текущая реализация выполняет путь стираний**, а не поиск неизвестных ошибок: CRC переводит обнаруженные повреждения в $e$. Под гарантией восстановления до двух фрагментов подразумеваются исправная таблица CRC, корректный заголовок и обнаружение фактических повреждений.

### 7.5. Численный пример: два отсутствующих фрагмента

$Y=\texttt{ABCDEF}$, $S=6$, $q=1$. Префикс длины и данные дают ровно 10 информационных байтов, заполнение не нужно:

```text
D0 D1 D2 D3 D4 D5 D6 D7 D8 D9
06 00 00 00 41 42 43 44 45 46
```

Матрица даёт $P_0=189=\mathtt{BD}$ и $P_1=148=\mathtt{94}$. Допустим, CRC пометила $D_0,D_1$ отсутствующими. Вычесть известные слагаемые из проверочных байтов (вычитание — XOR):

$$
\begin{aligned}
y_0&=P_0\oplus\bigoplus_{k=2}^{9}G_p[0,k]D_k=33,\\
y_1&=P_1\oplus\bigoplus_{k=2}^{9}G_p[1,k]D_k=83.
\end{aligned}
$$

Решается система **в GF(256)**:

$$
\begin{bmatrix}129&150\\150&129\end{bmatrix}
\begin{bmatrix}D_0\\D_1\end{bmatrix}
=\begin{bmatrix}33\\83\end{bmatrix},\qquad
A^{-1}=\begin{bmatrix}189&219\\219&189\end{bmatrix}.
$$

Отсюда $D_0=6$, $D_1=0$. Восстанавливается префикс длины, затем ровно `ABCDEF`. Счётчик исправлений равен **2**, независимо от количества изменённых байтов внутри этих двух фрагментов.

![Пошаговое решение для двух стираний](docs/figures/rs-alg.svg)

### 7.6. Что защита не гарантирует

- Сигнатура и флаги архива не входят в RS и не троируются.
- Таблица CRC32 находится вне RS. Её повреждение может ошибочно пометить исправный фрагмент или нарушить проверку.
- CRC допускает коллизии и не обеспечивает аутентификацию.
- После реконструкции код не выполняет повторную проверку всех CRC; при нуле несовпадений он также не проверяет уравнения parity.
- Более двух обнаруженных повреждённых фрагментов отклоняются, даже если каждый содержит только один изменённый байт.
- Защита — не шифрование; имена и содержимое не являются секретными.

## 8. Три копии заголовка

При `--protect` четырёхбайтовый заголовок блока записывается как `H | H | H`. Для каждой позиции `i` берутся байты $a,b,c$:

$$
H[i]=\begin{cases}
a,&a=b\text{ или }a=c,\\
b,&b=c,\\
\text{ошибка},&\text{все три различны}.
\end{cases}
$$

![Голосование трёх копий заголовка](docs/figures/triplication.svg)

Это **побайтовое**, не побитовое голосование. Разные позиции могут восстанавливаться из разных пар копий. Одна ошибочная копия каждого байта исправляется. Если две копии одного байта одинаково испорчены, неверное большинство принимается; если все три различны, архив отвергается. Троирование не позволяет обещать исправление любого сочетания «одна ошибка в каждом битовом разряде».

Пример для байта: `05 05 FF → 05`; `05 FF EE → ошибка`; `05 FF FF → FF`, хотя исходным мог быть 05. После голосования проверяются отношения `S ≤ N` и допустимость режима сжатия.

## 9. Побайтовый формат архива

Реализация: [`src/block/`](src/block/), [`src/archive/`](src/archive/), [`src/varint.rs`](src/varint.rs). В полях фиксированной длины многобайтовые числа записываются **little-endian**.

### 9.1. Заголовок архива

| Смещение | Длина | Поле |
|---:|---:|---|
| 0 | 8 | ASCII `CLARSv02`: `43 4C 41 52 53 76 30 32` |
| 8 | 1 | Флаги: бит 0 — LZ77, 1 — rANS, 2 — RS |

Биты 3…7 должны быть нулевыми; иначе формат отклоняется. Флаги едины для всего архива. По умолчанию `03`; с защитой по умолчанию `07`. Данные не обязаны сжиматься в каждом блоке, даже если эти биты установлены.

### 9.2. Блок без защиты

| Смещение от начала блока | Длина | Поле |
|---:|---:|---|
| 0 | 2 | `N − 1 : u16 LE` |
| 2 | 2 | `S − 1 : u16 LE` |
| 4 | S | Выбранный payload Y |

Уменьшение на 1 позволяет представить диапазон 1…65536 в 16 битах: `00 00 → 1`, `FF FF → 65536`. Нулевой блок отсутствует. CRC исходного блока и CRC заголовка не записываются.

### 9.3. Блок с защитой

| Смещение | Длина | Поле |
|---:|---:|---|
| 0 | 4 | Первая копия H |
| 4 | 4 | Вторая копия H |
| 8 | 4 | Третья копия H |
| 12 | 48 | CRC32 фрагментов D₀…D₉, P₀, P₁; по 4 байта LE |
| 60 | 10q | Информационные фрагменты, по q байт |
| 60 + 10q | 2q | Проверочные фрагменты, по q байт |

$q=\lceil(S+4)/10\rceil$. Поле `S` в H описывает **Y до RS**, а не длину CRC и фрагментов.

![Раскладка архива и защищённого блока](docs/figures/format.svg)

### 9.4. Логические записи внутри блочного потока

```text
Файл:
    01 | P : varint | имя : P байт UTF-8 | F : varint | содержимое : F байт
Папка:
    02 | P : varint | имя : P байт UTF-8
Конец:
    00
```

У папки нет полей `F` и содержимого. Пустой файл имеет `F=0`. Завершитель `00` — отдельная запись без имени и размера. После него не должно быть остатка декодированного блока, ожидающих блоков или дополнительных физических данных.

Имя хранится относительно корня извлечения с разделителем `/`. Корневая запись источника содержит его имя, а не абсолютный путь. При упаковке папка записывается перед детьми; дети сортируются по имени. Данные нескольких источников составляют один поток.

### 9.5. Unsigned LEB128 и битовые поля

$$
V=\sum_{i=0}^{k-1}(b_i\mathbin{\&}127)2^{7i}.
$$

Старший бит байта 1 означает продолжение, 0 — конец. Группы идут от младшей к старшей. Писатель выдаёт кратчайшую запись, читатель требует каноничность.

| Значение | Байты hex |
|---:|---|
| 0 | `00` |
| 127 | `7F` |
| 128 | `80 01` |
| 255 | `FF 01` |
| 300 | `AC 02` |
| 4096 | `80 20` |
| 65536 | `80 80 04` |

Предел для `u64` — 10 байт; в десятом допустимы только 0 или 1, но завершающая избыточная нулевая группа в многобайтовой записи отвергается. Например, `80 00` неканонично, `AC 82 00` неканонично. Отдельные читатели также накладывают предел значения: путь до 4096 байт, LZ77-длина до 65536, rANS-длина до 131075.

![Флаги, varint и смещённые поля](docs/figures/bits.svg)

### 9.6. Полный минимальный пример

Файл с именем `a` и одним байтом `A`; сжатие и защита выключены. Логический поток:

```text
01 01 61 01 41 00
│  │  │  │  │  └ конец архива
│  │  │  │  └ содержимое: A
│  │  │  └ размер файла 1
│  │  └ имя a
│  └ длина имени 1
└ тип: файл
```

`N=S=6`, поэтому заголовок блока равен `05 00 05 00`. Весь архив — 19 байт:

```text
43 4C 41 52 53 76 30 32 00
05 00 05 00
01 01 61 01 41 00
```

С `--protect`, но без сжатия: флаги `04`, заголовок блока троируется, `q=1`, RS payload занимает 60 байт. Итого `9 + 12 + 60 = 81` байт. Это пример контейнера, а не `Y=ABCDEF` из разбора матрицы.

## 10. Избыточность и эффективность

### 10.1. Точные функции размера

Для сохранённого payload $S$:

$$
\begin{aligned}
B_0(S)&=4+S,\\
q(S)&=\left\lceil\frac{S+4}{10}\right\rceil,\\
E(S)&=48+12q(S),\\
B_{RS}(S)&=12+E(S)=60+12q(S).
\end{aligned}
$$

$E$ — только защищённое содержимое после троированного заголовка; $B$ — весь физический блок. Архив из $m$ блоков занимает

$$
A=9+\sum_{i=0}^{m-1}B(S_i).
$$

Это не включает имя архива на файловой системе. Внутренние имена источников уже входят в исходные блоки и могут сжиматься.

Пусть $z=10q-(S+4)$ — число байтов заполнения, $0\le z\le9$. Тогда

$$
B_{RS}(S)=64+S+z+2q.
$$

Состав накладных расходов: 12 байт заголовков, 48 байт CRC, 4 байта внутреннего размера, $z$ заполнения и $2q$ parity. Сама RS-часть фрагментов имеет скорость $10/12=5/6$ и 20% проверочных байтов относительно информационной части. **Весь блок** имеет большие относительные расходы, особенно при малом S.

| S | q | Без RS: B₀ | С RS: B_RS |
|---:|---:|---:|---:|
| 1 | 1 | 5 | 72 |
| 6 | 1 | 10 | 72 |
| 64 | 7 | 68 | 144 |
| 256 | 26 | 260 | 372 |
| 1024 | 103 | 1028 | 1296 |
| 4096 | 410 | 4100 | 4980 |
| 65536 | 6554 | 65540 | 78708 |

При росте S на одну границу фрагмента размер RS-блока увеличивается сразу на 12 байт. Между границами он постоянен. При больших S отношение $B_{RS}(S)/S$ стремится к 1.2; при максимальном S=65536 дополнительный размер относительно payload составляет 13172 байта, около 20.10%.

[График дополнительных расходов RS для S = 1…64](docs/charts/rs-overhead_notion_agent_chart.html) — HTML с точными значениями при наведении. Он показывает $B_{RS}(S)-B_0(S)$: между границами расход уменьшается на байт, на границе добавления фрагмента возрастает на 11 байт. Это расчёт формата, не бенчмарк. Для просмотра скачайте HTML и откройте в браузере; GitHub не исполняет HTML из дерева репозитория.

### 10.2. Что считать коэффициентом сжатия

Необходимо указывать знаменатель. Для блока до защиты:

$$
\rho_{payload}=S/N,\qquad g_{payload}=1-S/N.
$$

Для всего архива, если исходные файлы занимают F байт:

$$
\rho_{archive}=A/F\quad(F>0).
$$

Эти показатели различаются: архив содержит имена, папки, завершающую запись, заголовки и, при защите, parity. Для набора только пустых файлов `F=0`, отношение не определено. Размер на диске с учётом кластеров файловой системы не равен размеру потока архива.

Статистика `original_bytes` считает содержимое файлов, а `compressed_blocks` и `stored_blocks` — блоки потока записей. Нельзя напрямую считать средний выигрыш блока из количества файлов или обещать ускорение T-кратное числу потоков.

## 11. Параллельность и ограничения

### 11.1. Партии и порядок

Локальный пул Rayon создаётся только когда есть более одного задания и `T > 1`. Размер партии:

$$
B(T)=\begin{cases}1,&T=1,\\\max(4,2T),&T>1.\end{cases}
$$

Результаты `map` собираются в исходном порядке. Чтение и запись партий последовательные, вычисления блоков могут идти параллельно. Каждый блок имеет собственный словарь и модель. На извлечении чтение физического потока формирует партию, затем блоки декодируются и выдаются в исходной последовательности.

![Партии, независимые задания и порядок](docs/figures/data-espd.svg)

Память зависит от размера партии, промежуточных LZ77/rANS-буферов, таблиц и защищённых данных. Нельзя приравнивать расход памяти ко `T × 64 КиБ`: одновременно хранятся исходные и промежуточные результаты. Потоки не создаются отдельно на каждый блок.

### 11.2. Имена и файловая система

| Проверка | Условие |
|---|---|
| Длина пути | 1…4096 байт UTF-8 |
| Глубина | До 128 компонентов |
| Длина компонента | До 255 байт |
| Число записей | До 100000 |
| Дубликаты | Проверяются после `to_lowercase()` |
| Родитель записи | Папка должна быть записана раньше ребёнка |
| Компоненты | Не пустые, не заканчиваются точкой/пробелом |
| Запрещённые символы | Управляющие, `/ \ : * ? " < > |` внутри компонента |
| Имена устройств | `con`, `prn`, `aux`, `nul`, `conin$`, `conout$` до первой точки |
| Ссылки | Symlink; на Windows также reparse point отклоняются |
| Тип источника | Только обычный файл или папка |

Точки `.` и `..` отклоняются правилом конечной точки. Это конкретный набор проверок, не заявление о полном покрытии всех зарезервированных имён всех ОС: например, `com1` и `lpt1` в списке кода не перечислены. Unicode-нормализация NFC не выполняется; регистронезависимое сравнение не является полной Unicode case-folding.

Архив, расположенный внутри исходной папки, исключается по каноническому пути. Размер файла фиксируется при открытии; слишком ранний конец или появление лишнего байта выявляются. Это не полноценный снимок файловой системы: изменение содержимого без изменения длины может остаться незамеченным.

### 11.3. Повреждения и безопасность

Обнаруживаются неизвестная сигнатура или флаги, обрыв чтения, неправильные размеры, неканонический varint, недопустимые ссылки LZ77, неверная модель/состояние rANS, более двух стираний RS, неоднозначное голосование заголовка, недопустимые записи и лишние данные после конца.

Без RS нет независимой контрольной суммы исходного блока. С RS гарантии ограничены условиями раздела 7.6. Нет шифрования, цифровой подписи, аутентификации и лимита общего объёма извлечения. Для недоверенного архива следует ограничивать свободное место и использовать изолированную среду. Проверки путей не делают весь процесс устойчивым к внешним конкурентным изменениям файловой системы.

## 12. Тестирование и контрольные векторы

Основной набор: [`tests/all.rs`](tests/all.rs). Он запускается отдельным harness-free исполняемым тестом:

```sh
cargo test --test all --locked
```

Набор содержит 18 проверок: сравнение LZ77 с эталонным поиском (в том числе 9841 короткий вход над алфавитом из трёх байтов), перекрытия и границы окна, модель и потоки rANS, формат блоков, RS и повреждения, порядок параллельного исполнения, команды и все восемь комбинаций флагов. Успех обозначается итогом `OK: 18`, `ERR: 0`.

| Проверяемый объект | Вход | Точный результат |
|---|---|---|
| LZ77 | ASCII ABABABA | `07 00 41 00 42 04 02 41` |
| rANS | ASCII ABAB | `04 01 41 42 80 10 00 50 00 08` |
| rANS | ASCII BANAN | `05 02 41 42 4E E6 0C B4 06 18 D9 A9 61` |
| rANS | ASCII AB × 16 | `20 01 41 42 80 10 AA 02 80 00 AA AA A8 00` |
| CRC32 | ASCII 123456789 | `CBF43926` как число |
| GF(256) | 0x80 × 0x02 | `1D` |
| RS parity | Payload ASCII ABCDEF; q=1 | `BD 94` |
| RS восстановление | Повреждение D₀ и D₁ этого payload | ABCDEF; счётчик 2 |

В [`tests/bench.rs`](tests/bench.rs) есть отдельный нагрузочный сценарий. Его можно запустить:

```sh
cargo test --release --test bench --locked
```

Числа времени и скорости зависят от сборки, процессора, хранения, входа, режима защиты и T. Для сравнения надо фиксировать эти параметры и хеши файлов; вывод одного запуска не устанавливает универсальную производительность. Документ не содержит результатов измерений на другой реализации или устаревшем формате.

## 13. Схемы и источники

Единый редактируемый источник — [docs/diagrams.drawio](docs/diagrams.drawio). Каждая страница соответствует SVG с тем же именем в `docs/figures/`; все 21 SVG включены в разделы выше. Палитра: фон и заполнение `#1f1e24`, линии `#b3afb9`, текст `#ececef`; Arial, основной текст 22, пояснения 18, заголовки 26.

В алгоритмических блок-схемах используются обозначения ГОСТ 19.701–90: прямоугольник — процесс, ромб — решение, параллелограмм — данные, терминатор — начало/конец. Стрелки задают направление, выходы решений подписаны «Да»/«Нет». Ленты байтов, таблицы интервалов и матрицы — **структурные иллюстрации**, а не алгоритмические блок-схемы; их ячейки не обозначают операции.

### Учебная основа

Курс **ОТИК**, Кононова Александра Игоревна, МИЭТ, СПИНТех, КАИ. Исходный проект: [illinc/otik](https://gitlab.com/illinc/otik). Номера страниц относятся к страницам PDF в предоставленном наборе.

1. `000_intro_infomsr_codes.pdf`, с. 5–7, 15–16, 19–21: мера информации, энтропия, схема кодирования, натуральный и смещённый код.
2. `030_noise_hamming_rs.pdf`, с. 3, 11–12, 22–30: избыточность, блоки, троирование, поля и систематические RS-коды.
3. `021_compress_chains_lz77.pdf`, с. 1–8: повторное вхождение, окно, длина/расстояние, поиск, варианты записи и эффективность ссылки.
4. `011_compress_letters_ac.pdf`, с. 2–9, 15: вероятностная модель, целочисленные частоты, интервалы и нормализация. Это источник методики разбора модели, а не утверждение, что архиватор реализует AC.
5. `032_Galois_fields.pdf`, с. 2–14: конечные поля, многочлены, модуль и операции; полином для GF(256) на с. 12.
6. `sem44-rs_2022.pdf`, с. 1–8: постановка кодирования и восстановления, пошаговые алгебраические примеры. Численные примеры матричного RS(12,10) в этом документе относятся к библиотеке архиватора, не к полиномиальному примеру семинара.
7. [reed-solomon-erasure 6.0.0](https://docs.rs/reed-solomon-erasure/6.0.0/reed_solomon_erasure/), `src/core.rs`, `src/matrix.rs`, `src/galois_8.rs`, `build.rs`: построение систематической матрицы и полином 0x11D.
8. [crc32fast 1.4.2](https://docs.rs/crc32fast/1.4.2/crc32fast/): CRC32 IEEE.

Учебные понятия используются для объяснения; спецификация двоичного формата и конкретных проверок задаётся исходным кодом CLARSLIB. Формулы, раскладки и примеры выше относятся только к CLARSv02.
