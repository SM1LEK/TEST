## Постановка задачи и требования

| Параметр | Значение |
| --- | --- |
| Версия формата | 2 (сигнатура CLARSv02) |
| Кодирование | LZ77 => rANS => Reed-Solomon (независимы) |
| Защита заголовков | Троирование (3 копии, побайтовое голосование) |
| Защита данных | Reed-Solomon erasure coding (10 data + 2 parity shards) |
| Размер исходного блока | 1..=65536 байт |
| Число потоков T | 1..=64; по умолчанию min(число процессоров, 64) |
| Размер партии | 1 блок при T = 1; max(4, 2T) при T > 1 |
| Порядок блоков | Исходный, результат не зависит от числа T |
| Словарь и модель | Отдельные для каждого блока |
| Выбор сжатого представления | При S < N |
| Создание архива | Только новый файл; существующий не перезаписывается |
| Извлечение | Только новая папка; исключение сбрасывает результат |
| Источники | Несколько файлов и папок, пустые файлы и папки, имена только в UTF8 |
| Ссылки и reparse points | Запрещены |
| Архив внутри исходной папки | Исключается из входных данных |

### Сборка и команды

Требуется Rust ≥ 1.88; зависимости закреплены в Cargo.lock. Расчётные примеры записаны в hex: числа с префиксом 0x, последовательности байтов — парами цифр.

~~~sh
cargo build --release --locked
cargo test --test all --locked
~~~

Исполняемый файл: target/release/arch; в Windows — arch.exe.

~~~sh
# Создать архив из файла и папки; LZ77 и rANS включены, RS выключен.
arch create backup.mrx report.txt photos

# Те же этапы с защитой; 4 рабочих потока.
arch create --protect --threads 4 backup.mrx report.txt photos

# Только rANS, без LZ77.
arch create --no-lz77 backup.mrx report.txt

# Без сжатия, но с защитой RS.
arch create --no-lz77 --no-rans --protect backup.mrx report.txt

# Просмотреть записи и полностью проверить читаемость потока.
arch info --threads 4 backup.mrx

# Извлечь в новую папку.
arch extract --threads 4 backup.mrx restored

# Имя источника, начинающееся с --, после разделителя не является параметром.
arch create -- backup.mrx --notes.txt
~~~

--no-lz77, --no-rans и --protect относятся к create; они должны стоять перед именем архива. --threads T допускается один раз до разделителя --, 1 ≤ T ≤ 64. Без параметра используется min(available_parallelism, 64), при невозможности определить параллельность — 1.

Если у имени архива нет расширения, добавляется .mrx; другое расширение отклоняется. Создание не перезаписывает существующий файл. Для извлечения нужна **несуществующая** папка. При ошибке созданный архив или папка извлечения удаляется; если удаление не удалось, это сообщается вместе с исходной ошибкой.

info не ограничивается чтением оглавления: оно декодирует блочный поток и проходит содержимое файлов, но не записывает файлы на диск. Статистика «Исправлено фрагментов» считает RS-фрагменты, а не исправленные байты.

### Модель данных и обозначения

#### Что является источником

Источник — поток байтов записей файлов и папок. Имена кодируются UTF-8, содержимое не преобразуется. Блоки до 64 КиБ; границы записей и блоков независимы.

| Обозначение | Смысл |
|---|---|
| X, N = \|X\| | Исходный блок потока записей; 1 ≤ N ≤ 65536 |
| C, K = \|C\| | Кандидат после включённых этапов сжатия |
| Y, S = \|Y\| | Сохранённые данные **до** RS; 1 ≤ S ≤ N |
| n | Длина входа отдельного вызова rANS; не обязательно равна N |
| D | Число разных байтов во входе rANS |
| v(s), f(s), c(s) | Число появлений, нормализованная частота, начало интервала |
| M = 4096 | Сумма нормализованных частот rANS |
| L = 2²³ | Нижняя граница и начальное состояние rANS |
| q в rANS | Остаток x mod M |
| q в RS | Длина одного фрагмента; контекст раздела отличает её от остатка |
| T | Число рабочих потоков |

#### Информация и кодирование

Для модели источника без памяти с вероятностями $p_s$ информация появления символа и энтропия равны:

~~~math
I(s)=-\log_2 p_s,\qquad H=-\sum_s p_s\log_2 p_s.
~~~

При равномерном алфавите из $D$ символов $H=\log_2 D$. Для независимых символов идеальная стоимость сообщения $s_0\ldots s_{n-1}$ составляет

~~~math
\ell_{\mathrm{ideal}}=-\sum_{i=0}^{n-1}\log_2 p_{s_i}.
~~~

rANS использует $p_s=f(s)/4096$. К этой стоимости добавляются модель, состояние, заголовки и защита; для короткого входа накладные расходы могут превысить выигрыш.

LZ77 заменяет повторяющиеся цепочки ссылками; rANS кодирует полученные байты. RS добавляет избыточность для восстановления.

## Структура архиватора

**Конвейер обработки блока.**

![Конвейер обработки блока](docs/figures/data.svg)

Заголовок архива хранит общие флаги режима (9 байт, сигнатура CLARSv02). При включённой защите заголовки блоков записываются тремя копиями (троирование), а данные блоков защищаются Reed-Solomon erasure coding. Побайтовое голосование большинства восстанавливает заголовки при повреждении одной из трёх копий.

Параллельные задания выполняются локальным пулом Rayon. Результаты записываются в исходном порядке.

### Выбор представления блока

Для блока $X$ сначала применяются только включённые этапы:

~~~math
C=\mathrm{rANS}_{\mathrm{opt}}(\mathrm{LZ77}_{\mathrm{opt}}(X)),
\qquad
Y=\begin{cases}C,& |C|\lt N,\\X,& |C|\ge N.\end{cases}
~~~

Отключённый этап тождественен. С исходным блоком сравнивается только результат комбинации, заданной флагами.

**Правило декодера:** S < N означает сжатое представление; тогда выполняются rANS, затем LZ77, если их флаги включены. При S = N оба этапа пропускаются. Отдельного бита «этот блок сжат» нет.

RS применяется после выбора Y. Независимые словари и модели позволяют параллельную обработку; ссылки между блоками отсутствуют.

Сравнение K < N происходит до RS. Размер защищённого блока монотонно зависит от S, поэтому меньший S не увеличивает его размер, но из-за заполнения фрагментов уменьшение S не всегда уменьшает физический размер защищённого блока.

### Параллельная обработка

Локальный пул Rayon создаётся только когда есть более одного задания и T > 1. Размер партии:

~~~math
B(T)=\begin{cases}1,&T=1,\\\max(4,2T),&T\gt 1.\end{cases}
~~~

Результаты map собираются в исходном порядке. Чтение и запись партий последовательные, вычисления блоков могут идти параллельно. Каждый блок имеет собственный словарь и модель. На извлечении чтение физического потока формирует партию, затем блоки декодируются и выдаются в исходной последовательности.

**Партии, независимые задания и порядок.**

![Партии, независимые задания и порядок](docs/figures/parallel.svg)

Память зависит от размера партии, промежуточных LZ77/rANS-буферов, таблиц и защищённых данных. Нельзя приравнивать расход памяти ко T × 64 КиБ: одновременно хранятся исходные и промежуточные результаты. Потоки не создаются отдельно на каждый блок.

### Имена и файловая система

| Проверка | Условие |
|---|---|
| Длина пути | 1…4096 байт UTF-8 |
| Глубина | До 128 компонентов |
| Длина компонента | До 255 байт |
| Число записей | До 100000 |
| Дубликаты | Проверяются после to_lowercase() |
| Родитель записи | Папка должна быть записана раньше ребёнка |
| Компоненты | Не пустые, не заканчиваются точкой/пробелом |
| Запрещённые символы | Управляющие, / \ : * ? " < > \| внутри компонента |
| Имена устройств | con, prn, aux, nul, conin$, conout$ до первой точки |
| Ссылки | Symlink; на Windows также reparse point отклоняются |
| Тип источника | Только обычный файл или папка |

Точки . и .. отклоняются правилом конечной точки. Это конкретный набор проверок, не заявление о полном покрытии всех зарезервированных имён всех ОС: например, com1 и lpt1 в списке кода не перечислены. Unicode-нормализация NFC не выполняется; регистронезависимое сравнение не является полной Unicode case-folding.

Архив, расположенный внутри исходной папки, исключается по каноническому пути. Размер файла фиксируется при открытии; слишком ранний конец или появление лишнего байта выявляются. Это не полноценный снимок файловой системы: изменение содержимого без изменения длины может остаться незамеченным.

### Повреждения и безопасность

Обнаруживаются неизвестная сигнатура или флаги, обрыв чтения, неправильные размеры, неканонический varint, недопустимые ссылки LZ77, неверная модель/состояние rANS, более двух стираний RS, неоднозначное голосование заголовка, недопустимые записи и лишние данные после конца.

Без RS нет независимой контрольной суммы исходного блока. С RS гарантии ограничены условиями подраздела «Что защита не гарантирует». Нет шифрования, цифровой подписи, аутентификации и лимита общего объёма извлечения. Для недоверенного архива следует ограничивать свободное место и использовать изолированную среду. Проверки путей не делают весь процесс устойчивым к внешним конкурентным изменениям файловой системы.

## Алгоритмы

### LZ77

| Параметр | Значение |
| --- | --- |
| Единица обработки | Байт |
| Окно | 4096 байт |
| Максимальная длина совпадения | 255 байт |
| Результат | Длина совпадения, расстояние, следующий байт: (l, d, c) |
| Хеш | По первым двум байтам; 4096 цепочек позиций |
| Равные длины | Ближайшее совпадение |

#### Ограничения ссылки

В позиции $p$ выбирается самое длинное совпадение в окне:

~~~math
\begin{aligned}
0&\le l\le\min(255,N-p-1),\\
1&\le d\le\min(4096,p)\quad(l\gt 0),\\
X[p-d+j]&=X[p+j]\quad(0\le j\lt l),\\
c&=X[p+l],\qquad p'=p+l+1.
\end{aligned}
~~~

Верхняя граница N − p − 1 оставляет один байт для c. Поэтому каждая тройка заканчивается литералом, в том числе последняя. При l = 0 расстояние не записывается; математически можно обозначать его нулём, но в потоке этого поля нет.

Флагового байта литералов и ссылок нет.

#### Поиск совпадения

Хешируются первые два байта:

~~~math
h(a,b)=\left(\big((a+256b)\times\mathtt{0x9E3779B1}\big)\bmod 2^{32}\right)\gg20.
~~~

Получаются 4096 цепочек позиций. Хеш лишь отбирает кандидатов: реальное совпадение проверяется побайтово, поэтому коллизия не превращается в неправильную ссылку.

1. Если допустимая длина не меньше 2, пройти цепочку от новых позиций к старым, пока расстояние не превышает 4096.
2. Сравнить байты до limit; заменить лучший результат только при **строго большей** длине.
3. При достижении limit поиск закончить — более длинного ответа нет.
4. Если совпадение длины ≥ 2 не найдено, проверить последнюю позицию текущего байта. Она может дать ссылку длины 1.
5. Внести в таблицы **все** пройденные позиции p … p + l, а не только начало тройки.

При равных длинах выбирается ближайшая ссылка. Все кандидаты в окне проверяются; глобальная оптимизация размера не выполняется.

**Блок-схема кодирования LZ77.** Слева — кодирование, справа — декодирование.

![Блок-схема кодирования LZ77](docs/figures/lz77-alg.svg)

#### Поток и стоимость тройки

~~~text
N : unsigned LEB128
повторять до конца потока:
    l : u8
    если l > 0: d : unsigned LEB128
    c : u8
~~~

Если $v(d)$ — число байтов varint, то тройка занимает

~~~math
t(l,d)=\begin{cases}2,&l=0,\\2+v(d),&l\gt 0.\end{cases}
~~~

Она описывает $l+1$ исходных байтов. Без учёта префикса и влияния последующего rANS локальный выигрыш есть при $l+1\gt 2+v(d)$. Например, ссылка длины 1 может увеличить поток LZ77. Кодер её всё равно записывает; окончательный выбор представления делает блочный уровень.

Наихудшая верхняя граница выхода LZ77 для блока — 3 + 2 × 65536 = 131075 байт: трёхбайтовая длина и по два байта на каждый литерал. Поэтому длина входа rANS после LZ77 может быть больше 65536.

#### Декодирование и перекрытие

После чтения тройки проверяются допустимое расстояние и l + 1 ≤ N − |R|. Копирование выполняется **по одному байту**:

~~~math
\text{повторить }l\text{ раз: }R\leftarrow R\,\|\,R[|R|-d],
\qquad R\leftarrow R\,\|\,c.
~~~

Текущий |R| увеличивается после каждого добавления. Поэтому при l > d источник следующих байтов может находиться среди только что восстановленных данных. Копирование фиксированного среза старого буфера не эквивалентно этому правилу.

#### Разбор ABABABA

| p | limit | l | d | c | Новая позиция |
|---:|---:|---:|---:|:---:|---:|
| 0x0 | 0x6 | 0x0 | — | A | 0x1 |
| 0x1 | 0x5 | 0x0 | — | B | 0x2 |
| 0x2 | 0x4 | 0x4 | 0x2 | A | 0x7 |

~~~text
07 | 00 41 | 00 42 | 04 02 41
 N    l  c    l  c    l  d  c
~~~

При третьей тройке буфер равен AB. Копируются позиции 0x00, 0x01, 0x02, 0x03; позиции 0x02 и 0x03 появились в ходе этой же ссылки. Затем литерал A завершает результат.

Размер потока 0x08 превышает вход 0x07; без rANS блочный кодер сохранит исходные байты.

Другие проверяемые случаи:

- AAAAAA → 06 00 41 04 01 41: l=0x04, d=0x01.
- 0x102 байта A: первая тройка-литерал, ссылка длины 0xFF с литералом, последний литерал.
- На позиции 0x06 в abXabYabZ выбирается d=0x03, а не 0x06 при длине 0x02.
- При limit = 0 совпадение не ищется: последний байт записывается явно.

### rANS

| Параметр | Значение |
| --- | --- |
| Состояние | Одно 32-битное целое x |
| Сумма частот M | 4096 = 2^12 |
| Нижняя граница L | 8388608 = 2^23 |
| Кодирование | Справа налево |
| Декодирование | Слева направо |

#### Статическая модель блока

Для ненулевого входа длины $n$ подсчитываются $v(s)$ и число присутствующих байтов $D$. Отсутствующим символам назначается частота 0. Присутствующим сначала назначается:

~~~math
\begin{aligned}
w_s&=v(s)(M-D),\\
f_s^{(0)}&=1+\left\lfloor\frac{w_s}{n}\right\rfloor,\\
r_s&=w_s\bmod n,\\
\Delta&=M-\sum_s f_s^{(0)},\qquad M=4096.
\end{aligned}
~~~

Добавить единицу первым $\Delta$ символам по убыванию $r_s$; при равенстве — по возрастанию байта. Получаются f(s) ≥ 1 и сумма M: деление определено, интервалы полностью разбивают таблицу состояний.

~~~math
c(s)=\sum_{t\lt s}f(t),\qquad [c(s),c(s)+f(s)).
~~~

**BANAN:** n=0x05, D=0x03, M−D=0xFFD. Символы в порядке значения байта: A, B, N.

| Символ | v | w | floor(w/n) | Остаток | Начальная f⁰ | Поправка | Итог f | c |
|:---:|---:|---:|---:|---:|---:|---:|---:|---:|
| A | 0x2 | 0x1FFA | 0x665 | 0x1 | 0x666 | 0x0 | 0x666 | 0x0 |
| B | 0x1 | 0xFFD | 0x332 | 0x3 | 0x333 | 0x1 | 0x334 | 0x666 |
| N | 0x2 | 0x1FFA | 0x665 | 0x1 | 0x666 | 0x0 | 0x666 | 0x99A |

Сумма начальных частот 0xFFF; остаток B максимален. После поправки интервалы покрывают [0,0x1000).

#### Переходы без перенормировки

Кодер начинает с $x=L=2^{23}$ и обрабатывает вход **справа налево**. Для символа $s$:

~~~math
C_s(x)=\left\lfloor\frac{x}{f(s)}\right\rfloor M+(x\bmod f(s))+c(s).
~~~

Декодер получает символы **слева направо**. Вычислить $q=x\bmod M$ и найти единственный $s$, для которого $c(s)\le q\lt c(s)+f(s)$. Затем:

~~~math
D_s(x)=f(s)\left\lfloor\frac{x}{M}\right\rfloor+q-c(s).
~~~

**Почему переход обратим.** Пусть $x=af+r$, $0\le r\lt f$. Тогда $C_s(x)=aM+r+c$. Остаток по $M$ равен $r+c$, поскольку интервал символа лежит внутри [0,M). Декодер выбирает тот же символ и получает $fa+(r+c)-c=af+r=x$.

#### Байтовая перенормировка

Чтобы состояние оставалось в 32-битном диапазоне, перед переходом кодер выполняет:

~~~math
\text{пока }x\ge 2^{19}f(s):\quad b=x\bmod256,\quad x\leftarrow\lfloor x/256\rfloor.
~~~

Байт $b$ откладывается. Порог в реализации равен

~~~math
((L\gg12)\ll8)f(s)=2^{19}f(s).
~~~

После обратного перехода декодер восстанавливает масштаб:

~~~math
\text{пока }x\lt L:\quad\text{прочитать }b,\quad x\leftarrow256x+b.
~~~

Поток хранит конечное состояние x : u32 LE, затем отложенные байты **в обратном порядке их выдачи**. Декодер начинает с последнего состояния, поэтому ему сначала нужен последний вынесенный байт. Проверка начального состояния: $L\le x\lt 256L=2^{31}$.

**Кодер, декодер и циклы перенормировки rANS.** Слева — кодирование, справа — декодирование.

![Кодер, декодер и циклы перенормировки rANS](docs/figures/rans-alg.svg)

После вывода ровно $n$ символов требуется одновременно x = L и отсутствие непрочитанных байтов. Эти проверки выявляют многие повреждённые потоки, но не являются криптографической проверкой содержимого.

#### Пример ABAB

Частоты f(A)=f(B)=0x800, начала интервалов c(A)=0, c(B)=0x800. Порог 0x40000000 не достигается, поэтому байты перенормировки отсутствуют. Прямой и обратный проход:

**Переходы состояния rANS для ABAB.** Слева — кодирование, справа — декодирование.

![Переходы состояния rANS для ABAB](docs/figures/rans.svg)

Последняя частота восстанавливается как 0x1000 − 0x800 = 0x800. Конечное состояние 0x08005000 записывается в LE:

~~~text
04 | 01 | 41 42 | 80 10 | 00 50 00 08
 n   D−1  алфавит  f(A)   состояние
~~~

Размер 0x0A превышает вход 0x04: блочный кодер сохраняет исходное представление.

#### Перенормировка: AB × 0x10

Вход — 0x20 байт, модель та же. На шаге 0x08 кодер обрабатывает A:

~~~text
x = 0x4002A800 ≥ 0x80000 × 0x800 = 0x40000000
выдать 00; x = floor(0x4002A800 / 0x100) = 0x4002A8
C_A(x) = 0x8002A8
~~~

Все вынесенные байты в порядке кодера: 00 A8 AA AA. В потоке они стоят как AA AA A8 00. Конечное состояние — 0x8002AA, то есть AA 02 80 00 в LE.

~~~text
20 | 01 | 41 42 | 80 10 | AA 02 80 00 | AA AA A8 00
 n   D−1  алфавит  f(A)       состояние    байты масштаба
~~~

Первый символ декодера — A: q=0x2AA; обратный переход даёт 0x4002AA < L. Чтение AA восстанавливает 0x100 × 0x4002AA + 0xAA = 0x4002AAAA. После 0x20 символов x=L, все байты прочитаны. Выход занимает 0x0E байт, меньше 0x20; при включённом LZ77 вход rANS будет другим.

#### Двоичное представление модели

~~~text
n : varint
если n = 0: поток заканчивается здесь (единственный байт 00)
D − 1 : u8
если D ≤ 32: D разных байтов по возрастанию
иначе: bitmap[32]; символ s задан битом (s mod 8) в байте floor(s / 8)
f(s₀), …, f(s_{D−2}) : varint
x : u32 LE
байты перенормировки
~~~

Последняя частота вычисляется вычитанием из 4096. При D = 1 частоты в потоке вообще не нужны: единственный символ имеет частоту 4096. Проверяются порядок алфавита, число битов карты, D ≤ n, положительность частот и наличие четырёх байтов состояния.

Длина отдельного потока rANS ограничена длиной возможного выхода LZ77; минимальный ненулевой заголовок — 7 байт (n, D−1, один символ, состояние). Предельная консервативная оценка заголовка в коде — 550 байт. Это верхняя оценка, а не фиксированная длина модели.

### CRC32

Реализация использует crc32fast 1.4.2. Контрольная сумма вычисляется **отдельно для каждого RS-фрагмента**, включая два проверочных. Она хранится как u32 LE в таблице перед фрагментами.

CRC32 соответствует отражённому алгоритму IEEE: начальный регистр 0xFFFFFFFF, отражённый полином 0xEDB88320, финальный XOR 0xFFFFFFFF. При табличном вычислении очередного байта $b$:

~~~text
index = (crc AND 255) XOR b
crc = (crc >> 8) XOR TABLE[index]
~~~

Таблица эквивалентна восьми битовым шагам с полиномом для каждого возможного младшего байта. 

**Вычисление CRC32.**

![Вычисление CRC32](docs/figures/crc32-flow.svg)

Контрольный вектор: ASCII 123456789 даёт **0xCBF43926**, в LE — 26 39 F4 CB. Для пустого входа результат равен 0.

CRC **обнаруживает**, но не исправляет. Несовпадение сообщает RS, какой фрагмент считать отсутствующим. Коллизии возможны; CRC не защищает от умышленной подмены. Без --protect таблицы CRC нет, и неверные, но синтаксически допустимые данные могут быть приняты.

### Reed-Solomon (erasure coding)

**Reed-Solomon erasure.**

![Reed-Solomon erasure](docs/figures/reed-solomon.svg)

| Параметр | Значение |
| --- | --- |
| Код | RS erasure (10 data + 2 parity shards) |
| Подготовка данных | original_len (u32 LE) + payload |
| Разбиение | ceil((len+4) / 10) байт на фрагмент |
| Кодирование | ReedSolomon::encode добавляет 2 проверочных фрагмента |
| Формат выхода | CRC32 таблица (12 x 4 байта) + тела фрагментов (12 x shard_size) |
| Обнаружение повреждений | CRC32 каждого фрагмента |
| Восстановление | До 2 утраченных фрагментов (стираний) |
| Более 2 повреждений | Ошибка |

Восстановление выполняется обращением матрицы исправных строк.

#### Арифметика поля

Каждый байт — многочлен степени < 8 с коэффициентами в GF(2):

~~~math
a=a_7z^7+\cdots+a_1z+a_0,\qquad a_i\in\{0,1\}.
~~~

Модуль поля библиотеки:

~~~math
P(z)=z^8+z^4+z^3+z^2+1\quad(\mathtt{0x11D}).
~~~

Сложение и вычитание совпадают с XOR. Умножение — произведение многочленов с остатком по $P(z)$. Для ненулевого $a$, $a^{255}=1$ и $a^{-1}=a^{254}$. Например,

~~~math
\mathtt{0x80}\times\mathtt{0x02}=z^8\equiv z^4+z^3+z^2+1=\mathtt{0x1D}.
~~~

Результат 0x1D получен редукцией многочлена, не обрезанием целочисленного произведения.

#### Как готовятся фрагменты

1. Добавить перед выбранным payload $Y$ его длину $S$ как u32 LE.
2. Выбрать $q=\lceil(S+4)/10\rceil$; для блоков S ≥ 1, поэтому q ≥ 1.
3. Дополнить нулями до 10q байт и разрезать на $D_0,\ldots,D_9$ по $q$ байт.
4. Получить $P_0,P_1$, тоже по $q$ байт.
5. Записать 12 CRC32 в порядке $D_0,\ldots,D_9,P_0,P_1$, затем сами фрагменты в том же порядке.

Заполнение выравнивает фрагменты; префикс S задаёт точную длину результата. 

#### Порождающая матрица

Для каждого смещения $j$ берётся столбец из 10 байтов $\mathbf d_j$. Библиотека строит матрицу Вандермонда и приводит её к систематическому виду:

~~~math
V_{i,k}=i^k\text{ в GF(256)},\quad
0\le i\lt 12,\ 0\le k\lt 10,\qquad
T=V_{0:10,:},\quad G=VT^{-1}=\begin{bmatrix}I_{10}\\G_p\end{bmatrix}.
~~~

Число $i$ в этой формуле — элемент поля с байтовым представлением i; $i^0=1$, включая строку i=0. Верхние 10 строк единичные, поэтому исходные фрагменты остаются без изменения. Коэффициенты проверочных строк:

~~~math
P_r[j]=\bigoplus_{k=0}^{9}G_p[r,k]\cdot D_k[j],\qquad r\in\{0,1\}.
~~~

**Систематическая матрица RS(12,10).** Коэффициенты в шестнадцатеричном представлении.

![Систематическая матрица RS(12,10)](docs/figures/rs-matrix.svg)

#### Восстановление и его предел

При чтении CRC каждого фрагмента сравнивается с таблицей. Несовпавший фрагмент заменяется на None. Если таких фрагментов больше двух, возвращается ошибка. При одном или двух библиотека выбирает исправные строки матрицы и восстанавливает неизвестные данные. При нуле реконструкция не вызывается.

Пусть $J$ — любые 10 исправных строк, $\mathbf y_J$ — соответствующие байты. Тогда

~~~math
\mathbf d=G_J^{-1}\mathbf y_J.
~~~

После реконструкции информационные фрагменты объединяются, читается внутренний $S$; проверяется $S\le10q-4$ и возвращается соответствующий срез. Внутренний размер не сравнивается непосредственно с аргументом _original_size; дальнейшие проверки блочного и энтропийного декодирования ограничивают допустимость результата.

Для абстрактного кода с двумя проверочными символами условие исправления смешанных ошибок и стираний имеет вид $2t+e\le2$, где $t$ — ошибки с неизвестными позициями, $e$ — известные стирания. **Текущая реализация выполняет путь стираний**, а не поиск неизвестных ошибок: CRC переводит обнаруженные повреждения в $e$. Под гарантией восстановления до двух фрагментов подразумеваются исправная таблица CRC, корректный заголовок и обнаружение фактических повреждений.

#### Численный пример: два отсутствующих фрагмента

$Y=\mathrm{ABCDEF}$, S=0x06, q=0x01. Префикс длины и данные дают ровно 0x0A информационных байтов, заполнение не нужно:

~~~text
D0 D1 D2 D3 D4 D5 D6 D7 D8 D9
06 00 00 00 41 42 43 44 45 46
~~~

Матрица даёт $P_0=\mathtt{0xBD}$ и $P_1=\mathtt{0x94}$. Допустим, CRC пометила $D_0,D_1$ отсутствующими. Вычесть известные слагаемые из проверочных байтов (вычитание — XOR):

~~~math
\begin{aligned}
y_0&=P_0\oplus\bigoplus_{k=2}^{9}G_p[0,k]D_k=\mathtt{0x21},\\
y_1&=P_1\oplus\bigoplus_{k=2}^{9}G_p[1,k]D_k=\mathtt{0x53}.
\end{aligned}
~~~

Система в GF(256); элементы матриц записаны в hex:

~~~math
\begin{bmatrix}\mathtt{81}&\mathtt{96}\\\mathtt{96}&\mathtt{81}\end{bmatrix}
\begin{bmatrix}D_0\\D_1\end{bmatrix}
=\begin{bmatrix}\mathtt{21}\\\mathtt{53}\end{bmatrix},\qquad
A^{-1}=\begin{bmatrix}\mathtt{BD}&\mathtt{DB}\\\mathtt{DB}&\mathtt{BD}\end{bmatrix}.
~~~

Отсюда D₀=0x06, D₁=0x00. Восстанавливается префикс длины, затем ровно ABCDEF. Счётчик исправлений равен 0x02, независимо от количества изменённых байтов внутри этих двух фрагментов.

#### Что защита не гарантирует

- Сигнатура и флаги архива не входят в RS и не троируются.
- Таблица CRC32 находится вне RS. Её повреждение может ошибочно пометить исправный фрагмент или нарушить проверку.
- CRC допускает коллизии и не обеспечивает аутентификацию.
- После реконструкции код не выполняет повторную проверку всех CRC; при нуле несовпадений он также не проверяет уравнения parity.
- Более двух обнаруженных повреждённых фрагментов отклоняются, даже если каждый содержит только один изменённый байт.
- Защита — не шифрование; имена и содержимое не являются секретными.

### Троирование заголовков

**Троирование.**

![Троирование](docs/figures/triplication.svg)

| Параметр | Значение |
| --- | --- |
| Принцип | Запись данных 3 раза подряд |
| Восстановление | Побайтовое голосование большинства (2 из 3) |
| Применение | Заголовки блоков при включённой защите |
| Исправление | До 1 полностью повреждённой копии |
| Все 3 копии различны | Ошибка |

#### Правило голосования и пределы защиты

При --protect четырёхбайтовый заголовок блока записывается как H | H | H. Для каждой позиции i берутся байты $a,b,c$:

~~~math
H[i]=\begin{cases}
a,&a=b\text{ или }a=c,\\
b,&b=c,\\
\text{ошибка},&\text{все три различны}.
\end{cases}
~~~

Это **побайтовое**, не побитовое голосование. Разные позиции могут восстанавливаться из разных пар копий. Одна ошибочная копия каждого байта исправляется. Если две копии одного байта одинаково испорчены, неверное большинство принимается; если все три различны, архив отвергается. Троирование не позволяет обещать исправление любого сочетания «одна ошибка в каждом битовом разряде».

Пример для байта: 05 05 FF → 05; 05 FF EE → ошибка; 05 FF FF → FF, хотя исходным мог быть 05. После голосования проверяются отношения S ≤ N и допустимость режима сжатия.

### Проверки формата и пример

#### Проверка флагов

Биты 3…7 должны быть нулевыми; иначе формат отклоняется. Флаги едины для всего архива. По умолчанию 03; с защитой по умолчанию 07. Данные не обязаны сжиматься в каждом блоке, даже если эти биты установлены.

#### Смещённые размеры блока

Уменьшение на 1 позволяет представить диапазон 1…65536 в 16 битах: 00 00 → 1, FF FF → 65536. Нулевой блок отсутствует. CRC исходного блока и CRC заголовка не записываются.

#### Смещения полей защищённого блока

| Смещение | Длина | Поле |
|---:|---:|---|
| 0 | 4 | Первая копия H |
| 4 | 4 | Вторая копия H |
| 8 | 4 | Третья копия H |
| 12 | 48 | CRC32 фрагментов D₀…D₉, P₀, P₁; по 4 байта LE |
| 60 | 10q | Информационные фрагменты, по q байт |
| 60 + 10q | 2q | Проверочные фрагменты, по q байт |

$q=\lceil(S+4)/10\rceil$. Поле S в H описывает **Y до RS**, а не длину CRC и фрагментов.

#### Границы логических записей

~~~text
Файл:
    01 | P : varint | имя : P байт UTF-8 | F : varint | содержимое : F байт
Папка:
    02 | P : varint | имя : P байт UTF-8
Конец:
    00
~~~

У папки нет полей F и содержимого. Пустой файл имеет F=0. Завершитель 00 — отдельная запись без имени и размера. После него не должно быть остатка декодированного блока, ожидающих блоков или дополнительных физических данных.

Имя хранится относительно корня извлечения с разделителем /. Корневая запись источника содержит его имя, а не абсолютный путь. При упаковке папка записывается перед детьми; дети сортируются по имени. Данные нескольких источников составляют один поток.

#### Unsigned LEB128 и битовые поля

~~~math
V=\sum_{i=0}^{k-1}(b_i\bmod128)2^{7i}.
~~~

Старший бит байта 1 означает продолжение, 0 — конец. Группы идут от младшей к старшей. Писатель выдаёт кратчайшую запись, читатель требует каноничность.

Предел для u64 — 10 байт; в десятом допустимы только 0 или 1, но завершающая избыточная нулевая группа в многобайтовой записи отвергается. Например, 80 00 неканонично, AC 82 00 неканонично. Отдельные читатели также накладывают предел значения: путь до 4096 байт, LZ77-длина до 65536, rANS-длина до 131075.

#### Полный минимальный пример

Файл с именем a и одним байтом A; сжатие и защита выключены. Логический поток:

~~~text
01 01 61 01 41 00
│  │  │  │  │  └ конец архива
│  │  │  │  └ содержимое: A
│  │  │  └ размер файла 1
│  │  └ имя a
│  └ длина имени 1
└ тип: файл
~~~

N=S=0x06, поэтому заголовок блока равен 05 00 05 00. Весь архив — 0x13 байт:

~~~text
43 4C 41 52 53 76 30 32 00
05 00 05 00
01 01 61 01 41 00
~~~

С --protect, но без сжатия: флаги 04, заголовок блока троируется, q=0x01, RS payload занимает 0x3C байта. Итого 0x09 + 0x0C + 0x3C = 0x51 байт.

### Расчёт физического размера

Для сохранённого payload $S$:

~~~math
\begin{aligned}
B_0(S)&=4+S,\\
q(S)&=\left\lceil\frac{S+4}{10}\right\rceil,\\
E(S)&=48+12q(S),\\
B_{RS}(S)&=12+E(S)=60+12q(S).
\end{aligned}
~~~

$E$ — только защищённое содержимое после троированного заголовка; $B$ — весь физический блок. Архив из $m$ блоков занимает

~~~math
A=9+\sum_{i=0}^{m-1}B(S_i).
~~~

Имена источников входят в исходный поток.

Пусть $z=10q-(S+4)$ — число байтов заполнения, $0\le z\le9$. Тогда

~~~math
B_{RS}(S)=64+S+z+2q.
~~~

Состав накладных расходов: 12 байт заголовков, 48 байт CRC, 4 байта внутреннего размера, $z$ заполнения и $2q$ parity. Сама RS-часть фрагментов имеет скорость $10/12=5/6$ и 20% проверочных байтов относительно информационной части. **Весь блок** имеет большие относительные расходы, особенно при малом S.

| S | q | Без RS: B₀ | С RS: B_RS |
|---:|---:|---:|---:|
| 0x1 | 0x1 | 0x5 | 0x48 |
| 0x6 | 0x1 | 0xA | 0x48 |
| 0x40 | 0x7 | 0x44 | 0x90 |
| 0x100 | 0x1A | 0x104 | 0x174 |
| 0x400 | 0x67 | 0x404 | 0x510 |
| 0x1000 | 0x19A | 0x1004 | 0x1374 |
| 0x10000 | 0x199A | 0x10004 | 0x13374 |

При переходе границы фрагмента RS-блок увеличивается на 0x0C байт. Между границами он постоянен. При больших S отношение $B_{RS}(S)/S$ стремится к 1.2; при максимальном S=0x10000 дополнительный размер относительно payload составляет 0x3374 байта, около 20.10%.

### Показатели эффективности

Необходимо указывать знаменатель. Для блока до защиты:

~~~math
\rho_{payload}=S/N,\qquad g_{payload}=1-S/N.
~~~

Для всего архива, если исходные файлы занимают F байт:

~~~math
\rho_{archive}=A/F\quad(F\gt 0).
~~~

Эти показатели различаются: архив содержит имена, папки, завершающую запись, заголовки и, при защите, parity. Для набора только пустых файлов F=0, отношение не определено. Размер на диске с учётом кластеров файловой системы не равен размеру потока архива.

Статистика original_bytes считает содержимое файлов, а compressed_blocks и stored_blocks — блоки потока записей. Нельзя напрямую считать средний выигрыш блока из количества файлов или обещать ускорение T-кратное числу потоков.
