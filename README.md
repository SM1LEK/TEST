### 1.3 Обозначения и единицы

| Обозначение | Смысл |
| --- | --- |
| X, N=\|X\| | Исходный блок потока записей; 1 ≤ N ≤ 65536 |
| C, K=\|C\| | Кандидат после всей включённой комбинации сжатия |
| Y, S=\|Y\| | Сохранённое представление до RS; 1 ≤ S ≤ N |
| B | Четырёхбайтовый заголовок блока: N−1 и S−1 |
| H | Общий заголовок: сигнатура и флаги, 9 байт |
| n, D | Длина входа одного вызова rANS и число разных байтов во входе |
| v(s), f(s), c(s) | Число появлений байта s; его нормализованная частота; начало интервала |
| M=4096, L=8388608 | Сумма частот и нижняя граница состояния rANS |
| x, q | Состояние rANS; q=x mod M. В разделе RS длина фрагмента обозначена h |
| U, h, E(U) | Длина произвольного payload RS; h=ceil((U+4)/10); длина RS-слова |
| T, b(T) | Число потоков и число блоков в партии |
| F, A | Сумма размеров содержимого файлов; полный размер архива в байтах |

### 1.4 Количество информации и фактический размер

Для модели без памяти p(s)=v(s)/n. Информация появления байта I(s)=−log₂p(s), энтропия H₀=−Σp(s)log₂p(s), оценка сообщения nH₀=−Σv(s)log₂p(s). Это оценка информационной части относительно выбранной модели, без заголовков и таблицы частот.

Для ASCII `BANAN`: n=5, p(A)=p(N)=2/5, p(B)=1/5. H₀≈1,521928 бит/байт; nH₀≈7,609640 бит. Исходные данные занимают 40 бит. rANS с моделью и состоянием занимает 13 байт = 104 бита. Противоречия нет: короткий пример имеет большие служебные расходы. Блочный уровень отказывается от такого сжатия.

LZ77 использует повторяемость цепочек. rANS использует распределение байтов своего входа, в том числе байтов команд LZ77. Поэтому энтропию исходного текста нельзя автоматически считать энтропией промежуточного потока.

## 2 Архитектура и блочный конвейер

Модули файловых записей передают общий поток в блочный слой. Сжатие и защита выполняются независимо для каждого блока; следующий рисунок связывает операции записи и чтения.

[![Рисунок 2 — Прямой и обратный конвейер v3](docs/figures/data.svg)](docs/figures/data.svg)

Рисунок 2 — Прямой и обратный конвейер v3.

### 2.1 Где выполняется каждый шаг

`cli::run` разбирает команду и параметры. `archive::create_with_options` открывает новый архив, обходит источники и передаёт записи в `BlockWriter`. `BlockWriter::write` набирает блоки до 65536 байт, `queue_block` собирает партию, `flush_batch` кодирует её и последовательно записывает результаты.

`archive::unpack::process` используется и для `extract`, и для `info`. Он получает логические записи через `BlockReader`. Читатель сначала голосует по общему заголовку, затем `read_stored` читает и проверяет физические поля блока. `decode_block` восстанавливает RS и снимает сжатие. Метод `Read::read` выдаёт исходные байты записей в нужном порядке.

### 2.2 Как выбирается представление

Для каждой пары флагов строится один кандидат:

| LZ77 | rANS | Кандидат C |
| --- | --- | --- |
| 0 | 0 | Не строится; сохранить X |
| 1 | 0 | LZ77(X) |
| 0 | 1 | rANS(X) |
| 1 | 1 | rANS(LZ77(X)) |

Если K<N, Y=C и S=K; иначе Y=X и S=N. Равенство размеров не является выигрышем. При двух включённых этапах программа не сравнивает отдельно X, LZ77(X) и rANS(X): проверяется только результат заданной комбинации. Это нужно для однозначного обратного прохода без отдельного набора флагов на каждый блок.

Ключевой фрагмент: [src/block/writer.rs](src/block/writer.rs), строки 29–32.

```rust
    // Неравенство размеров служит признаком сжатого блока в формате.
    let raw_bytes = ((raw_size - 1) as u16).to_le_bytes();
    let stored_bytes = ((stored.len() - 1) as u16).to_le_bytes();
    let header: [u8; BLOCK_HEADER_SIZE] =
```

Здесь `raw` — X, `raw_size` — N, `compressed` — необязательный кандидат C, `stored` — выбранный Y. `Some` означает наличие кандидата; `_` охватывает его отсутствие и все случаи без выигрыша. Этот фрагмент сохраняет исходный блок при любом отсутствии выигрыша. После выбора заголовок B содержит размеры **до RS**. Защита добавляется и к несжатому блоку, если включён `--protect`.

[![Рисунок 4 — Решение о сжатии и отдельная защита B и Y](docs/figures/block-choice.svg)](docs/figures/block-choice.svg)

Рисунок 4 — Решение о сжатии и отдельная защита B и Y.

### 2.3 Почему S<N достаточно декодеру

У сжатого блока все включённые этапы снимаются: rANS, затем LZ77. У блока с S=N оба этапа пропускаются. Проверки `S≤N` и допустимости режима исключают ссылку на несуществующий декодер. После восстановления размер результата должен быть ровно N.

Словарь LZ77 и модель rANS независимы для каждого блока. Межблочных ссылок нет. Изменение числа потоков меняет расписание работы, но не формат и не байтовый результат.

## 3 Логический поток и LEB128

### 3.1 Записи файловой системы

```text
Файл:  01 | P:LEB128 | имя:P байт UTF-8 | F:LEB128 | содержимое:F байт
Папка: 02 | P:LEB128 | имя:P байт UTF-8
Конец: 00
```

P — длина имени в байтах, не в буквах; F — размер содержимого. Папка не имеет поля F. Пустой файл имеет F=0. Корневой источник сохраняется под собственным именем, без абсолютного пути. Дочерние записи папки сортируются по `file_name`, сама папка записывается первой.

Блочный слой режет этот общий поток, а не каждый файл отдельно. Если осталось два места в блоке, начало имени или LEB128 может попасть в этот блок, а продолжение — в следующий. Интерфейсы `Write` и `Read` скрывают эти границы от `pack_file` и `process`.

[![Рисунок 6 — Байтовые записи и независимость файловых и блочных границ](docs/figures/records.svg)](docs/figures/records.svg)

Рисунок 6 — Байтовые записи и независимость файловых и блочных границ.

### 3.2 Unsigned LEB128

В каждом байте младшие семь бит — данные, старший — продолжение. Младшая группа числа записывается первой. Для байтов b₀…bₖ₋₁:

```text
V = Σ (b_i & 127) · 2^(7i)
```

| Число, dec | Байты hex | Число байтов |
| --- | --- | --- |
| 0 | 00 | 1 |
| 127 | 7F | 1 |
| 128 | 80 01 | 2 |
| 300 | AC 02 | 2 |
| 4096 | 80 20 | 2 |
| 65536 | 80 80 04 | 3 |

[![Рисунок 7 — Разложение 300 на 7-битовые группы и обратный расчёт](docs/figures/leb128-example.svg)](docs/figures/leb128-example.svg)

Рисунок 7 — Разложение 300 на 7-битовые группы и обратный расчёт.

Ключевой фрагмент: [src/varint.rs](src/varint.rs), строки 7–14.

```rust
        let more = value >= 128;
        output.write_all(&[(value as u8 & 0x7F) | ((more as u8) << 7)])?;
        value >>= 7;
        if !more {
            return Ok(());
        }
    }
}
```

`value` — ещё не записанная часть числа V, `output` — выходной поток байтов. `more` показывает, останутся ли группы после текущей. Маска `0x7F` оставляет данные; `more<<7` ставит бит продолжения. Затем число сдвигается на 7 разрядов. Для значения 0 цикл всё равно пишет один байт `00`.

Читатель принимает не более 10 байтов для u64. В десятом допустим только младший значащий бит. Многобайтовая запись, заканчивающаяся нулевой группой, отклоняется: `80 00`, `AC 82 00` неканоничны. `read_bounded` дополнительно проверяет предел значения: например, путь ≤4096, исходный блок LZ77 ≤65536, вход rANS ≤131075 байт.

### 3.3 Little-endian и смещённые размеры

Little-endian относится к фиксированным u16/u32, а LEB128 задаёт собственный порядок групп. Для u16: 256 хранится как `00 01`. В заголовке блока хранится N−1, поэтому N=256 даёт `FF 00`. Смещение на 1 использует все 65536 комбинаций u16 для положительных длин 1…65536; нулевого физического блока нет.

## 4 LZ77: поиск, команды и восстановление

### 4.1 Вариант алгоритма в проекте

Реализация заменяет совпавшую цепочку на тройку (l,d,c): длина совпадения, расстояние назад и обязательный следующий явный байт. Для l=0 расстояние отсутствует в потоке. Это конкретный вариант LZ77; в лекции 021 также рассматриваются варианты с флаг-битом и без обязательного литерала. Их упаковку нельзя переносить в CLARSv03.

В позиции p используются начала предыдущих вхождений из окна max(0,p−4096)…p−1. Сравниваемая цепочка может «свешиваться» за p: допускается перекрытие. Ограничения:

```text
0 ≤ l ≤ min(255, N−p−1)
1 ≤ d ≤ min(4096,p), если l>0
X[p−d+j] = X[p+j], j=0…l−1
c=X[p+l]; следующая позиция p′=p+l+1
```

N−p−1 оставляет место для c. Последний байт всегда явный. Предел 255 выбран форматом однобайтовой длины команды; окно 4096 ограничивает расстояние и поиск. Расстояния до 127 занимают один байт LEB128, от 128 до 4096 — два.

### 4.2 Хеш-цепочки и предел 512

Первые два байта a,b образуют little-endian число a+256b. Хеш:

```text
h(a,b) = (((a+256b) · 0x9E3779B1) mod 2^32) >> 20
```

Получается индекс 0…4095. `heads` хранит последние позиции корзин; `previous` связывает более старые позиции; `last_byte` хранит последнее появление каждого отдельного байта. Коллизия хеша даёт дополнительного кандидата, но не неправильную ссылку: совпадение всё равно проверяется побайтово.

Поиск идёт от новых позиций к старым, не далее 4096 байтов и не более чем по **512 кандидатам**. Учитываются и кандидаты, совпавшие только из-за коллизии хеша. Лучшее совпадение заменяется только при строго большей длине ≥2. При достижении limit функция сразу возвращает результат. Если совпадения ≥2 нет, допускается ссылка длины 1 на `last_byte`, если она ещё в окне.

Ключевой фрагмент: [src/lz77/matcher.rs](src/lz77/matcher.rs), строки 38–40.

```rust

            while candidate != NONE && position - candidate <= WINDOW && candidates < MAX_CANDIDATES
            {
```

В условии `candidate` — позиция проверяемого вхождения, `position` — p, `candidates` — уже просмотренное число позиций, `WINDOW=4096`, `MAX_CANDIDATES=512`, `NONE=usize::MAX` означает отсутствие позиции. Ограничение `candidates<MAX_CANDIDATES` означает: выбирается лучшее среди просмотренных, а не гарантированно самое длинное среди всех позиций окна. При равных длинах среди просмотренных сохраняется ближайшее вхождение, так как оно проверено раньше. Декодер от способа поиска не зависит.

В таблицы вставляются все пройденные позиции p…p+l. Если вставлять только начало команды, последующие цепочки не будут отражать весь уже пройденный текст.

### 4.3 Формат и стоимость команды

```text
N : LEB128
повторять:
    l : u8
    если l>0: d : LEB128
    c : u8
```

Пусть v(d) — число байтов расстояния. Команда занимает 2 байта при l=0 и 2+v(d) при l>0, описывая l+1 исходных байтов. Изолированная ссылка выгодна только при l+1>2+v(d). Программа не оптимизирует стоимость каждой команды: даже l=1 может быть записано, хотя увеличивает LZ77-поток. Затем rANS меняет стоимость его байтов, а окончательное решение принимает блочный уровень.

Консервативная граница выхода — 3+2N≤131075 байт: до трёх байтов префикса и не более двух на каждый исходный байт. Команда со ссылкой описывает несколько байтов и не ухудшает эту границу. Грубая верхняя оценка поиска на позицию — 512·255=130560 сравнений, память таблиц — O(N+4096+256).

### 4.4 Полный пример ABABABA

X=`41 42 41 42 41 42 41`, N=7. Первые A и B записываются явно. При p=2 доступно совпадение с p−d=0, d=2. Его длина ограничена четырьмя байтами, чтобы оставить A для литерала. Получается (4,2,A).

[![Рисунок 14 — Все команды ABABABA и точные выходные байты](docs/figures/lz77.svg)](docs/figures/lz77.svg)

Итог `07 00 41 00 42 04 02 41`, 8 байт вместо 7. Это работа отдельного LZ77, а не обещание сжатого физического блока. В режиме только LZ77 `encode_block` сохранит исходный X.

Для `AAAAAA` поток равен `06 00 41 04 01 41`. Для 258 байтов A: `82 02 00 41 FF 01 41 00 41` — явный A, ссылка длины 255 с литералом A, затем последний явный A. Эти случаи показывают границу длины и обязательный литерал.

### 4.5 Два кандидата и одинаковая длина

В `abXabYabZ` на p=3 цепочка `ab` совпадает с позицией 0 и обрывается на X≠Y. На p=6 ближайший кандидат — позиция 3, d=3; более дальний — позиция 0, d=6. Оба могли бы дать l=2. Ближайший достигает limit=2, поэтому второй уже не проверяется. Это не два фактически выполненных сравнения, а объяснение возможного равенства.

### 4.6 Декодирование с перекрытием

Читатель проверяет расстояние, доступность байтов команды и остаток объявленной длины. Затем каждый байт ссылки копируется из текущего, уже выросшего результата:

Ключевой фрагмент: [src/lz77/mod.rs](src/lz77/mod.rs), строки 65–68.

```rust
        for _ in 0..length {
            output.push(output[output.len() - distance]);
        }
        output.push(byte[0]);
```

В фрагменте `output` — результат R, `length` — l, `distance` — d, `byte[0]` — явный байт c. При l=4,d=2 буфер сначала равен `AB`. Получаются `ABA`, `ABAB`, `ABABA`, `ABABAB`; затем литерал A завершает `ABABABA`. На третьем и четвёртом копировании источник создан этой же ссылкой. ## 5 rANS: модель, состояния и байтовый поток

### 5.1 Модель и нормализация

rANS — целочисленный энтропийный код со стековым состоянием. Он использует одну статическую модель на вызов, а не адаптивное изменение частот после каждого байта. Включённый LZ77 меняет его вход: n тогда является размером LZ77-потока, а не исходного блока.

Подсчитать v(s), D и n. Неприсутствующим байтам назначить f=0; каждому присутствующему заранее выделить единицу. Оставшиеся M−D единиц распределяются пропорционально v:

```text
M = 4096
w(s) = v(s)·(M−D)
f₀(s) = 1 + floor(w(s)/n)
r(s) = w(s) mod n
Δ = M − Σ f₀(s)
```

Добавить единицу Δ символам с наибольшими r(s), при равенстве — в порядке возрастания байта. Это обеспечивает f(s)≥1 для присутствующих байтов и Σf=M. Фиксированный порядок делает модель воспроизводимой. Например, для ASCII `ABC` начальные частоты (1365,1365,1365) дают 4095 и равные остатки. Первая поправка достаётся меньшему байту A: итог (1366,1365,1365). Начало интервала c(s)=Σf(t) по всем t<s; интервалы [c(s),c(s)+f(s)) образуют разбиение [0,M).

В фрагменте `remainders` содержит пары (r(s),s): поле `.0` — остаток, `.1` — значение байта; `a` и `b` — две сравниваемые пары. `sum` — сумма начальных частот, `TOTAL=4096`, поэтому `take(TOTAL−sum)` выбирает ровно Δ пар. Массив `frequencies` хранит f(s).

Ключевой фрагмент: [src/rans/model.rs](src/rans/model.rs), строки 124–128.

```rust
    // Одинаковые остатки упорядочиваются по байту для воспроизводимости архива.
    remainders.sort_by(|a, b| b.0.cmp(&a.0).then(a.1.cmp(&b.1)));
    for &(_, symbol) in remainders.iter().take((TOTAL - sum) as usize) {
        frequencies[symbol] += 1;
    }
```

### 5.2 Прямой и обратный переходы

Кодер начинает с L=2²³=8388608 и обходит вход справа налево. Для текущего байта s:

```text
C_s(x) = floor(x/f(s))·M + (x mod f(s)) + c(s)
```

Декодер берёт q=x mod M, определяет s по c(s)≤q<c(s)+f(s), затем:

```text
D_s(x) = f(s)·floor(x/M) + q − c(s)
```

Почему переход обратим: запишем x=a·f+r, 0≤r<f. Тогда C_s(x)=aM+r+c. Внутри нужного интервала q=r+c, а floor(C_s(x)/M)=a. Обратный переход даёт fa+(r+c)−c=af+r=x. В отличие от арифметического кодирования из лекции 011, здесь не сужается вложенный интервал всего сообщения: интервалы модели выбирают остаток состояния.

### 5.3 Байтовая перенормировка

Перед переходом кодер уменьшает слишком большое состояние и сохраняет отделённые младшие байты:

```text
T(s) = ((L >> 12) << 8)·f(s) = 2^19·f(s) = 524288·f(s)
пока x ≥ T(s):
    выдать x & 255
    x >>= 8
после этого применить C_s(x)
```

После обратного перехода декодер увеличивает слишком малое состояние:

```text
пока x < L:
    прочитать b
    x = (x << 8) | b
```

Порог зависит от частоты конкретного символа. Он получается из выбранных L, M и байтового основания 256. Начальное состояние декодера обязано лежать в [L,256L), то есть [8388608,2147483648). После n символов проверяются одновременно x=L и полное исчерпание байтов перенормировки. Модель строится один раз: подсчёт O(n), сортировка остатков O(D log D), заполнение таблицы декодера O(4096). Сам проход линейный: при x<2³¹ и пороге не ниже 2¹⁹ для одного символа достаточно не более двух сдвигов на 8 бит.

В приведённом фрагменте `state` — x, `frequency` — f(s), `threshold` — T(s), `symbol` — индекс байта s, `starts[symbol]` — c(s), `TOTAL` — M, `emitted` — список отделённых байтов.

Ключевой фрагмент: [src/rans/mod.rs](src/rans/mod.rs), строки 27–34.


### 5.7 Как записывается модель

```text
n : LEB128
если n=0: конец; код единственный 00
D−1 : u8
если D≤32: список D байтов по возрастанию
иначе: bitmap[32], бит s%8 байта s/8 отмечает s
```

В рисунке `popcount` — число единичных битов всей 32-байтовой карты. Последняя частота равна M−сумма предыдущих; при D=1 частоты не записываются вообще. ## 6 CRC32: от битового шага к таблице

### 6.1 Назначение и параметры

В `ecc::encode` CRC32 вычисляется отдельно для каждого из 12 фрагментов. При чтении несовпадение превращает этот фрагмент в известное стирание для RS. CRC обнаруживает повреждение, а исправление выполняет RS. Без `--protect` этих CRC в архиве нет.

Используется `crc32fast` 1.4.2, CRC32 IEEE: начальный регистр 0xFFFFFFFF, отражённый полином 0xEDB88320, финальный XOR 0xFFFFFFFF. Контрольный вектор ASCII `123456789` даёт 0xCBF43926. В потоке это u32 LE `26 39 F4 CB`. Пустой вход даёт 0.

### 6.2 Один битовый переход

```text
crc = 0xFFFFFFFF
для каждого входного байта b:
    crc ^= b
    8 раз:
        если crc & 1: crc = (crc >> 1) XOR 0xEDB88320
        иначе:       crc = crc >> 1
результат = crc XOR 0xFFFFFFFF
```

Это логически эквивалентный разбор результата библиотеки. Он не означает, что `crc32fast` буквально выполняет такой цикл: библиотека использует ускоренные реализации.

### 6.3 Байтовый табличный переход

Таблица TABLE из 256 элементов заранее сворачивает восемь битовых шагов для каждого возможного младшего байта. Тогда один байт обрабатывается так:

## 7 Reed-Solomon: поле, матрица, восстановление

### 7.1 Применяемый код

`reed-solomon-erasure` 6.0.0 предоставляет систематический код над GF(256): 10 информационных и 2 проверочных фрагмента. Систематический означает, что первые 10 фрагментов остаются исходными. Каждое смещение внутри фрагмента — отдельный столбец из 12 байтов. Поэтому при длине фрагмента h байтов кодируется h независимых столбцов RS(12,10).

CRC сообщает позиции стираний. Программа восстанавливает до двух отмеченных фрагментов одного RS-слова. Это не обещание исправить две произвольные ошибки с неизвестными позициями. Для общего кода условие 2t+e≤2, где t — неизвестные ошибки, e — известные стирания; текущий путь реализует стирания e.

### 7.2 Байт как элемент поля

Биты a₇…a₀ задают многочлен a₇z⁷+…+a₁z+a₀ над GF(2). Модуль библиотеки P(z)=z⁸+z⁴+z³+z²+1, hex 11D (285). В `build.rs` используется младшая часть 1D, потому что старший член z⁸ учитывается при редукции.

Сложение и вычитание — XOR. Умножение — произведение многочленов с остатком по P. Это отличается от целочисленного умножения modulo 256. Например, 0x80·0x02=z⁸≡z⁴+z³+z²+1=0x1D.

При переносе за восьмой разряд редукция выполняется XOR с 0x11D. Например, 0xAE<<1=0x15C, 0x15C XOR 0x11D=0x41. Модуль 0x11B дал бы иные значения в байтовом представлении; его в расчётах CLARSv03 применять нельзя.

Для a≠0 выполняется a²⁵⁵=1, следовательно a⁻¹=a²⁵⁴. Например, 0x08·0xAD=1. Это позволяет делить коэффициенты при обращении матрицы.

Ненулевые элементы поля образуют цикл степеней α=0x02: α⁰=1,…,α²⁵⁴,α²⁵⁵=1. Дискретный логарифм logα(a) — номер степени, дающей ненулевой байт a. Поэтому a·b=α^((logα(a)+logα(b)) mod 255). Нуль обрабатывается отдельно и логарифма не имеет.

Для 0x57 и 0x83: логарифмы 189 и 247; (189+247) mod 255=181, α¹⁸¹=0x31. Обратный к 0x08=α³ равен α²⁵²=0xAD. Таблица показывает, где при последовательных сдвигах впервые требуется редукция.

### 7.3 Подготовка фрагментов и CRC

Для payload длины U добавить префикс U:u32 LE. Выбрать h=max(1,ceil((U+4)/10)), дополнить нулями до 10h и разрезать на D₀…D₉. Затем библиотека рассчитывает P₀,P₁ той же длины. Для всех 12 фрагментов вычислить CRC; записать сначала таблицу 48 байт, затем все фрагменты.

```text
RS(payload) = CRC32[12] | D₀ | … | D₉ | P₀ | P₁
E(U) = 48 + 12·max(1,ceil((U+4)/10))
```

Префикс возвращает точную исходную длину без заполнения. При защите блока код вызывается дважды: для B длиной 4, затем для Y длиной S. У каждого вызова свои 12 CRC и независимый бюджет двух стираний.

### 7.4 От Вандермонда к систематической матрице

Библиотека строит V[i,k]=iᵏ в GF(256), i=0…11,k=0…9. Значение i — байтовое представление элемента поля; i⁰=1, в том числе при i=0. Первые 10 строк образуют обратимую T. Затем G=V·T⁻¹. Верх G равен I₁₀; нижние две строки дают коэффициенты parity:

```text
P_r[j] = XOR по k=0…9 (G[10+r,k] · D_k[j]), r=0,1
```

Каждая операция выполняется в поле. Именно эта матричная реализация используется проектом. Полиномиальные примеры над GF(5) и Z₇ из 030 и sem44 объясняют код, но их коэффициенты, синдромы и модуль нельзя выдавать за расчёты данного архиватора.

### 7.6 Декодирование и два стирания

Читатель проверяет физическую длину 48+12h. Для каждого фрагмента сравнивает CRC с таблицей, несовпавшие передаёт библиотеке как `None`. Если e>2, немедленно возвращает ошибку. Если e=1 или 2, вызывается `reconstruct`; при e=0 реконструкция пропускается.

Ключевой фрагмент: [src/ecc.rs](src/ecc.rs), строки 90–98.

```rust
    if repaired > PARITY_SHARDS as u64 {
        return Err(invalid("Слишком много повреждённых фрагментов"));
    }

    if repaired > 0 {
        codec()
            .reconstruct(&mut shards)
            .map_err(|_| invalid("RS не удалось восстановить фрагменты"))?;
    }
```

`repaired` — число e обнаруженных стираний; `PARITY_SHARDS=2`; `shards` — массив фрагментов, где `None` отмечает отсутствующие. `codec()` возвращает переиспользуемый RS-кодек.

В общем случае берутся любые 10 исправных строк G_J и соответствующий столбец y_J. Информационный столбец d=G_J⁻¹·y_J. Библиотека использует первые доступные строки для построения системы. Если утрачены только проверочные фрагменты, информационные данные уже известны, и восстанавливается parity.

Для двух неизвестных D₀,D₁ достаточно удалить известные вклады из P₀,P₁. Остатки y₀=21 hex,y₁=53 hex. Получается система с A=[81 96;96 81] hex. Её определитель 08 hex ненулевой, обратная матрица [BD DB;DB BD] hex. Подстановка возвращает D₀=06,D₁=00.

### 7.7 Граница защиты

В одном фрагменте может измениться много байтов — это всё ещё одно стирание, если CRC его обнаружила. По одному испорченному байту в трёх разных фрагментах — уже три стирания и отказ. Для v3 заголовок блока и payload защищены независимо: допустимы по два обнаруженных стирания в каждом из двух слов.

[![Рисунок 53 — Какие повреждения входят в бюджет восстановления](docs/figures/rs-failure-budget.svg)](docs/figures/rs-failure-budget.svg)

Рисунок 53 — Какие повреждения входят в бюджет восстановления.

Гарантия относится к обнаруженным стираниям при корректных метках и параметрах. CRC-таблица находится вне RS; повреждённая запись может дать ложное стирание. Совпадение CRC при коллизии оставляет повреждённый фрагмент «исправным». После реконструкции все CRC повторно не проверяются; при нуле несовпадений уравнения parity отдельно не проверяются. Общий заголовок защищён троированием, а не этим кодом. Шифрования и аутентификации нет.

## 8 Троирование общего заголовка

### 8.1 Что троируется в v3

H=`CLARSv03 | flags`, 9 байт. `BlockWriter::with_threads` всегда записывает H|H|H, 27 байт, включая режим без RS. Защита сигнатуры и режима не зависит от защиты данных. Заголовки блоков B в v3 не троируются: без RS они обычные, с RS проходят отдельное кодирование длиной 60 байт.

Рисунок 54 — Два различных способа защиты общего и блочного заголовков.

### 8.2 Побайтовое большинство

Для каждой позиции i=0…8 берутся a=H₀[i],b=H₁[i],c=H₂[i]. Если a=b или a=c, принять a; иначе если b=c, принять b; иначе ошибка. Это голосование целых байтов, не отдельных битов.

В фрагменте Rust `a`, `b`, `c` — целые массивы трёх копий H, `i` — текущая позиция, `result` — восстанавливаемый заголовок. В правиле выше теми же буквами обозначены взятые из массивов байты.

Ключевой фрагмент: [src/block/mod.rs](src/block/mod.rs), строки 22–30.

```rust
        if a[i] == b[i] || a[i] == c[i] {
            result.push(a[i]);
        } else if b[i] == c[i] {
            result.push(b[i]);
        } else {
            return None;
        }
    }
    Some(result)
```

Рисунок 55 — Алгоритм голосования и последующая проверка сигнатуры.

Рисунок 56 — Восстановление при разных повреждённых позициях трёх копий.

Одна испорченная копия каждого байта исправляется; целиком исправной копии может не быть. Если две копии одного байта одинаково повреждены, ложное большинство принимается. Три разных значения означают отсутствие решения. После голосования проверяются сигнатура `CLARSv03` и нулевые неизвестные биты 3…7. Тесты троирования используют учебный массив из четырёх байтов, но реальный общий заголовок имеет девять.

| --- | --- | --- |

| С RS | RS(B) \| RS(Y) | 60+48+12·ceil((S+4)/10) |

### 9.5 Размер и избыточность

Для сохранённого payload S≥1:

```text

E(S) = 48 + 12h(S)
B₀(S) = 4 + S
B_RS(S) = E(4) + E(S) = 108 + 12h(S)
A = 27 + Σ B(S_i)
```

Обозначим z=10h−(S+4), 0≤z≤9. Тогда B_RS(S)=112+S+z+2h. Расходы: 60 байт защищённого B, 48 байт CRC слова Y, 4 байта внутренней длины Y, z заполнения и 2h проверочных байтов. Скорость кода фрагментов — 10/12=5/6; проверочных байтов 20% относительно информационных фрагментов. Полные расходы архива больше, особенно на коротких блоках.

## 10 Параллельность, пути и обработка ошибок

### 10.1 Партии и исходный порядок

Потоки T∈[1,64]. По умолчанию min(available_parallelism(),64), при ошибке определения — 1. Партия b(T)=1 при T=1 и max(4,2T) при T>1. Пул Rayon создаётся при выборе T>1, даже если впоследствии окажется одно задание. Партия из одного элемента обрабатывается последовательно внутри уже выбранного Executor.

`items` — упорядоченный список блоков, `operation` — функция кодирования или декодирования блока, `pool` — локальный пул Rayon. Варианты `Sequential` и `Parallel` выбирают последовательный или параллельный путь.

Ключевой фрагмент: [src/parallel.rs](src/parallel.rs), строки 49–55.

```rust
        match self {
            Self::Sequential => Ok(items.into_iter().map(operation).collect()),
            Self::Parallel { pool, .. } if items.len() > 1 => {
                Ok(pool.install(|| items.into_par_iter().map(operation).collect()))
            }
            Self::Parallel { .. } => Ok(items.into_iter().map(operation).collect()),
        }
```

Рисунок 62 — Несовпадение порядка завершения и порядка записи блоков.

`into_par_iter` для Vec — индексируемый параллельный итератор. Сборка результатов в Vec сохраняет порядок. `flush_batch` затем записывает этот Vec по очереди. На чтении партия физических блоков декодируется параллельно, складывается в `VecDeque` и выдаётся в исходном порядке. Чтение и запись потока остаются последовательными.

Дополнительный объём исходных блоков партии не более b(T)·65536 байт; это не оценка всей памяти. Одновременно существуют исходные, промежуточные и защищённые буферы, таблицы поиска и модели, ожидающие результаты и пул потоков. Для T=64 партия содержит 128 блоков, только их исходные данные занимают 8 МиБ. Время и память всей программы не равны T×скорость одного блока и T×64 КиБ.

| Тип источника | Обычный файл или папка; symlink/reparse point отклоняются |

[![Рисунок 63 — Проверки путей, порядок создания и откат](docs/figures/paths.svg)](docs/figures/paths.svg)

Рисунок 63 — Проверки путей, порядок создания и откат.

Точки `.` и `..` отклоняются как компоненты, заканчивающиеся точкой. Полное Unicode case-folding и нормализация NFC не выполняются. `com1` и `lpt1` в списке запрещённых имён кода отсутствуют; возможен последующий отказ файловой системы. Поэтому документация не приписывает коду полный список имён Windows.

Сам создаваемый архив исключается из обхода по каноническому пути. `pack_file` фиксирует длину файла, проверяет ранний конец и появление лишнего байта после чтения ожидаемой длины. Изменение содержимого с сохранением длины этот механизм не обязан обнаружить; это не снимок файловой системы.

### 10.3 Успех и откат

Создание открывает архив через `create_new(true)`. Извлечение сначала создаёт новый корневой каталог. Ошибка упаковки удаляет незавершённый архив, ошибка извлечения — созданный каталог вместе с частично извлечёнными файлами. Если очистка сама завершилась ошибкой, исходное сообщение дополняется описанием очистки. Существующие результаты не являются объектом отката.

`info` может напечатать некоторые записи до обнаружения повреждения дальше по потоку; вывод списка не означает окончательного успеха. Полная проверка заканчивается только после успешного `reader.finish()` и всех проверок конца.

### 10.4 Проверки повреждённого формата

| Уровень | Причины отказа |
| --- | --- |
| Общий заголовок | Нет большинства; сигнатура не CLARSv03; неизвестные флаги |
| Физический блок | Обрыв; S>N; сжатие при выключенных обоих кодерах; слишком короткий непустой rANS |
| RS | Неверная длина слова; e>2; неудача реконструкции; внутренняя длина за доступными данными |
| LZ77 | Недопустимая длина потока; ссылка за результат; d=0 при l>0; превышен N; неверный итоговый размер |
| rANS | Некорректный алфавит/частоты; недопустимое состояние; обрыв перенормировки; остаток байтов; x≠L |
| Записи | Неизвестный тип; пустой/некорректный путь; дубликат; отсутствующий родитель; обрыв содержимого |
| Окончание | После 00 остались декодированные байты, ожидающие блоки или физические данные |

Без RS нет независимой контрольной суммы исходного блока. Некоторые изменения могут сохранить синтаксически допустимый поток. С RS действуют условия обнаружения и бюджета стираний из раздела 7. Нет шифрования, цифровой подписи и лимита общего объёма извлечения; эти функции не следует описывать как существующие.

### 10.5 Что означает вывод info и extract

| Поле вывода | Что считается |
| --- | --- |
| Файлов / папок | Число логических записей соответствующего типа; папки включают корни источников |
| Исходные файлы | Сумма F содержимого файлов; без имён, папок и метаданных |
| Архив | Физическая длина файла .mrx |
| LZ77 / rANS / защита | Общие режимы из восстановленного H |
| Сжатых блоков | Число прочитанных блоков с S<N |
| Блоков без сжатия | Число блоков с S=N |
| Исправлено фрагментов | Сумма отмеченных стираний RS по заголовкам B и данным Y; не число байтов |

`info` печатает записи через обратный вызов `on_entry` и только после полного успешного прохода — итоговую статистику. `extract` печатает статистику после завершения извлечения. Блоки не совпадают с файлами, поэтому число файлов не определяет число сжатых блоков.

### 11.3 Методика измерения полного архиватора

15.10.2026, Windows x86_64, Rust 1.99.0, release, один рабочий поток. Каждый вход — файл `data` длиной 1048576 байт. Один прогрев, затем пять измерений; приведена медиана. Отсчёт ведётся вокруг полного запуска `arch create` и `arch extract`, включает запуск процесса, файловый ввод-вывод и `sync_all`. Кэш ОС не очищался, фоновые процессы не изолировались. Малые различия времени одного прогона не доказывают превосходство режима.

Наборы: A — одинаковые байты 0x41; текст — период ASCII `one two three four\n`; 256 — циклические 0…255; случайный — xorshift32, seed=0x12345678, сдвиги 13/17/5 с приведением к u32 после левых сдвигов, в выход берётся младший байт; смешанный — тот же случайный поток, в котором чётные блоки по 65536 байт заменены A. Нумерация блоков с нуля.

Скорость V=F/(t·1048576), где F — байты содержимого файла, t — секунды. Экономия=100·(1−A/F), A — весь архив с метаданными. Эти величины отличаются от S/N отдельного блока до RS.
